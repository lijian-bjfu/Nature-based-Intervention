## 一、总体思路

**原理**

1. 埋点的核心是被试在虚拟世界中的行为。数据要能识别被试在什么时间、什么位置做了什么，至少能看出行为在空间和时间上的整体变化趋势。
2. 埋点不是结果变量。按意向治疗的分析逻辑（见《实验设计A》2.1），组间比较不依赖埋点；埋点用于说明交互组接收了多少提供的刺激，以及交互组内部发生了什么。
3. 数据分三层处理。事实层：什么时间、在哪里、做了什么、系统如何回应、当时世界里发生了什么，这是日志要记的全部。分类层：常规还是异常（失败点击、被挡、反复折返等），分类规则以后可能改，所以离线做，不写进日志。解释层：动机，日志只能显示做了什么，动机要结合回放、访谈和问卷推测。
4. App 只记原始量，指标全部离线计算。原始数据完整，指标定义改了可以重算；在 App 里算好再存，定义一改数据就作废。
5. 日志字段必须与实际判定函数同源，不在记录代码里另做一套判断（9 月分析中"停止光圈半径"、10 月发现的"移动结果"列错误均属此类）。

**做法**

- 被试行为分为三部分：空间位置、点击、环视。按性质组织为两条流：连续的位姿流（位置、视线朝向、手指是否在屏），以及离散的输入事件流（点击、长按后退、拖动的开始与结束，每个事件附带系统的回应）。"环视"横跨两条流：拖动的起止是输入事件，转了多少、停在哪个方向是位姿。点击触发的转向是系统对点击的回应，不是被试的动作，单独标明。
- "什么都没做"（停留、凝视）只能从位姿流识别，因此位姿流必须常开、不能丢。
- 世界一侧的事件（剧本事件、飞行生物惊飞、声音提示）用来解释行为，与行为数据使用同一时钟、落在同一会话中。
- 指标层（访问频率、停留时长、覆盖范围、点击趋势等）暂缓，记录层定完后再讨论。

## 二、时间

**原理**

1. 分析行为趋势需要一个从会话开始单调递增的时钟。
2. 与生理数据（LSL）对齐需要一个绝对时间。PolarBridge 装在手机上，所有数据包用 iOS 系统时间（Unix 秒）作时间戳，电脑端据此换算到 LSL 时钟；虚拟自然 APP 装在 iPad 上，按既定分工不与电脑通信，只能以 iPad 系统时间作绝对时间，依靠两台设备各自自动校时保持一致（相差通常在几十毫秒以内）。
3. 行为与生理指标的对齐按几十秒到几分钟的时间窗进行，不是实验的主要方法；即使对不齐，也可以单独分析游戏内行为。因此这一精度足够。

**做法**

- 单位为秒，记到毫秒（三位小数）。
- 两套时钟：会话内时间（从进入场景起算，单调递增，App 切到后台时也按真实时间推进）；绝对时间为 iPad 系统时间（Unix 秒）。
- 现有日志使用的 `Time.time` 是游戏时钟，不满足上述要求，需更换（见附：待办）。
- 实验操作：手机与 iPad 都打开"自动设置时间"，实验前联过网；每场实验在进入实验条件时，实验员在 PolarBridge 中打一个标记，事后与 APP 记录的进入时刻比较，用于核对该场次的时钟偏差。

## 三、空间坐标

**原理**

1. 场景是约 100×100 m 的局部世界，只以奥大山为蓝本，不对应真实地理位置，不需要经纬度。Unity 世界坐标本身是以米为单位的直角坐标系，计算距离和停留范围最直接，且与编辑器里看到的数字一致。
2. 坐标的意义依赖场景不变；场景原点或地形位置一旦移动，已采集的坐标就全部错位。

**做法**

- 使用 Unity 世界坐标：X 东西、Z 南北、Y 高度，水平与高度原点都沿用世界坐标原点。单位为米，记到厘米（两位小数）。
- 记录相机的 X、Y、Z 和脚下地面高度。相机 Y 是眼睛高度，混有站立、下蹲和地形高低；与地面高度相减即可区分。
- 爬坡与高差不单独记录，离线从相机高度和地面高度推算。它反映的是路线选择（是否上坡、是否到高处远眺），不是体力消耗。被陡坡挡住的情况已记在点击日志的受阻原因中。
- 朝向用角度制（视线偏航、俯仰），规范中需写明 0° 所指方向。
- 正式实验开始后，场景原点与地形位置不得再移动。会话信息不记场景版本（2026-10-22 定）。

## 四、区域与景点

区域与景点是叠加在坐标之上的标注层，不影响 APP 要记录什么：只要时空表完整，范围画好后导出成表，即可离线判断被试所在的区域和景点；范围不合适可修改后重算。

**方法（已议，待制作）**

- 区域：用"贴地折线"画首尾相接的多边形，贴合异形边界。只有路上、区域之间的过渡点附近需要画准；密林、陡坡、水里等走不到的地方可以往外画宽，相邻区域在那里互相重叠也没关系。离线只看水平位置是否落在多边形内；落在所有区域之外的点由程序报出，补画即可。
- 景点：用圆形标记（中心 + 半径）。"在景点附近"即离中心若干米以内；改半径即可重算。点击和触摸按命中位置归到景点。
- 导出：菜单工具把所有区域多边形与景点圆导出成一张表（名称、顶点坐标或中心与半径），与实验数据放在一起供分析。
- 时机：改完日志代码之后制作。

## 五、第一层：时空表

**原理**：用于了解被试在整个干预期间的时间与空间分布，例如在哪里停留更久、移动多还是站着多。走了多远、移动还是静止、在哪里停留，都由位置离线算出，属于指标层，不在表中记录。

**做法**

- 单独一张表，每 0.1 秒记一行（每秒 10 行）。时间单位仍为秒，记录实际时刻，保留三位小数。
- 列：会话内时间、系统时间、相机 X、Y、Z、脚下地面高度、画面朝向（左右朝向、俯仰，角度制）。
- 画面朝向是画面实际朝向（身体朝向与头部偏角之和），不是调试面板上"头相对身体"的角度。加入它的理由：旁观者回放必须有逐帧朝向，才能还原被试当时看到的画面；可看停留时面向哪里（如面向水面还是林子）；可用来核对环视表的起止朝向。

## 六、第二、三层：点击表、后退表、环视表

**原理**

1. 手指接触屏幕的操作按性质分表，避免一张表里大半列为空。点击关心"打中什么、走没走过去、摸没摸到"；环视关心"转了多少、转了多久"。
2. 长按后退本质上类似撤销，与环境互动关系较弱；但它会在时空表中留下一段倒退轨迹，不记录就无法解释。利用率预计不高，主要供日后核对数据时调用。
3. 点击表只记对行为分析有用的内容。想走、实走、按压时长、射线穿透等属于技术排查信息，不进点击表，仍保留在开发用的调试日志中。
4. 受阻是"按设计该走的距离被路径判定截短"，不是"没走到点击点"：按设计，点地面会在点击点前停下，点植物、石头会停在观看或伸手距离。受阻分两种，含义可能不同：半路被截是部分成功；起步受阻（尤其在同一处反复出现）更像在跟操作较劲。受阻能否预测无聊、如何解释，属于指标层，记录层只保证两种分开记录。另需注意：越爱探索的人越容易走到边界、被挡越多，受阻多不一定意味着体验差。

**做法**

- 三张表：点击表（一行一次点击）、后退表（一行一次长按后退）、环视表（一行一段转动）。三表共用时间列和一个触屏序号（每次手指接触屏幕加一），可按时间合并还原操作顺序，也可发现漏记。
- 点击表的列：

| 列 | 内容 |
|---|---|
| 触屏序号 | 与其他操作表共用 |
| 会话内时间、系统时间 | 点击判定的时刻 |
| 被试位置 X、Y、Z | 点击时相机位置；与命中位置连起来可看出被试想往哪里去 |
| 判定 | 无 / 走过去 / 走近去看 |
| 命中层 | 打中物体所在的层 |
| 命中位置 X、Y、Z | 用于日后判断点击发生在哪个区域、景点 |
| 是否触碰 | 最终有没有摸到（需走近、蹲下后才伸手的，记最终结果） |
| 受阻类型 | 无 / 半路被截 / 起步受阻 |
| 受阻原因 | 空气墙·密林坡地 / 空气墙·水域 / 迈不上去（一步升高 > 0.7 m）/ 落差太大（一步下降 > 1.2 m）/ 太陡（路上坡度 > 55°）/ 无地面 |

- 不记命中对象名称：场景中同名物体很多，事后无法逐条查找；需要时用命中层加命中位置，或在旁观者回放中定位查看。
- 后退表的列：触屏序号、时刻（会话内时间、系统时间）、开始时的位置、退了多远、受阻类型与原因。

**环视表**

- 原理：画面朝向由身体朝向与头部偏角相加而成。拖动转的是头，点击后转向目标转的是身体；每次点击时程序还会把头的偏角并入身体（头归零、身体加同样角度，画面不动）。因此只看调试面板上的"环顾 yaw"会漏掉点击转身，并把内部换算误认为转动。环视应监测画面实际朝向，转动原因由代码在发起转动时标注。
- 一行记一段转动：从画面开始转，到停稳为止（"开始转""停稳"各用一个小阈值，如角速度低于每秒 2° 算停稳，改代码时定）。
- 类型两种：拖拽式（手指拖动及松手后的惯性）；点击式（点击后身体转向目标，含过桥沿路线转向；点可触摸植物后俯仰跟随；点地面后俯仰回到平视）。
- 列：触屏序号（拖拽式填该次拖动的序号，点击式填引起它的点击的序号，可与点击表对应）、开始与结束时刻（会话内时间、系统时间）、开始与结束朝向（左右朝向、俯仰）、转动量（左右、俯仰各转了多少度）、类型。
- 来回晃动的识别：多次短拖动方向交替，看连续几行净转动量正负交替；一次拖动内左右来回，看累计转动量是否远大于净转动量；也可从时空表逐 0.1 秒的朝向曲线细看。数据只说明转动的样子，分不出是控制不稳、找路还是随手乱划，属于解释层。

**空气墙分类**

- 空气墙按挡住的对象分两类：密林坡地、水域。陡坡与密林不再细分。
- 用标签区分，不分物理层：每段空气墙带一个"阻挡类型"字段，在 Inspector 中选择；行走判定不变，只在被挡住时读出类型写入日志。不改物理层，是因为行走判定和其他系统都按 `EnvBarrier` 一层识别空气墙，拆层需同步修改所有引用。
- 横跨两类的空气墙（如一段墙前半挡陡坡密林、后半挡水域）不截断：在挡水的那一段放一个"水域标记框"，作为这面墙的子物体。标记框只用于记录，不挡路、不可见。
- 判定规则：被挡住时先确定撞到的是哪一面墙，只检查这面墙名下的标记框；被挡位置（只看水平范围，不看高度）落在框内记"水域"，否则记这面墙自己的类型。别的墙名下的框不起作用，因此标记框罩到相邻的墙也没关系。整面都挡水的墙直接设为"水域"，不需要标记框。

## 七、世界事件

**原理**

1. 日志只记录世界做了什么，以及被试对它有没有明确的行为反应。"被试是否注意到、是否被吸引"是心理状态，日志测不出来：判断是否看到某只生物需要记录每只生物的连续位置并结合朝向与遮挡计算，数据量大且只是近似；即使算出出现在画面里，也不等于注意到或被吸引。这与第五节放弃"景物是否进入视野"的理由相同。
2. 飞行系统（游荡的蝴蝶、蜜蜂、蜻蜓等）与植物、溪流一样是场景的一部分，属于提供的剂量，对每个交互组被试相同，在方法部分说明，不单独记录。
3. 被试对生物的明确反应已有记录：点击飞行生物（点击表 `hit_layer = Creature`）、伸手惊飞停落个体（惊飞事件）。"有没有被吸引"留给访谈（如"有没有注意到场景里的动物"）和旁观者回放的个案分析。

**做法**

- 世界事件在分析中只有两个用处：报告接收剂量（多少被试遇到了鸟群、惊飞过蝴蝶）；解释个别行为（某一刻停下、转头时有没有事件发生）。因此实验数据表只记三种行：事件发生、到结束未发生（附原因）、手惊飞常驻生物。触发过程的各阶段（进入范围、等视线、飞行起止等）不进实验数据表，留在开发用调试日志中。
- 剧本事件日志已能说明：被试是否遇到某事件；未触发是因为没走到还是走到了但没往那边看；鸟群飞过时在画面内可见的秒数；停落个体是否被手惊飞。

## 八b、文件与写盘规范

**存储位置（已定）**

- APP 不联网，数据写在 iPad 本机：APP 的文稿（Documents）目录。打包时打开 iOS 文件共享，使数据可在 iPad"文件"App 中看到，或用线连 Mac 后在访达中拖出。编辑器测试时仍写在工程的 `Logs~` 文件夹。
- 不使用第三方分析服务（如 Google Analytics）：被试行为数据会存到第三方服务器，伦理上不合适；数据被汇总抽样，拿不到原始记录；且需要联网。
- 不使用 iCloud：没有公共账户，用个人（研究者或学生）的 iCloud 存在隐私问题。
- 数据安全靠操作规矩：不删除 APP，更新只用覆盖安装（APP 标识不变，数据保留）；每天实验结束后把数据拷到实验室电脑并核对文件数。APP 主菜单显示"本机已存有 N 场数据"，便于实验员核对。
- 伦理申请中数据存储位置写：iPad 本机、研究者电脑。
- 拷出后的数据存入项目主目录 `data/` 下对应数据集的 `raw/app/`（正式实验 `data/formal/`，预实验与测试 `data/pilot_and_test/`），原始输入统一从那里读取并保持只读；清理与格式化表保存到对应数据集的 `processed/app/`，最终分析表放 `final/`，补充数据放 `supplementary/`；图、描述结果与报告写入 `reports/formal/app/` 或 `reports/pilot_and_test/app/`，按工作内容分类而不按数据集建报告目录；固定字段与工程规范来自 `00_settings.py`，日常运行与描述展示参数在 `01_parameters.py` 修改；由 `02_run.py` 统一调度，支持 VS Code 点 Run 与命令行。结构与使用规范见根目录 `README.md`。

**文件夹与命名（已定）**

- 每进入一次模块生成一个文件夹，命名与研究者 LSL 文件的写法一致：`NBI_Data/sub-P040_ses-S001_mod-Interactive_run-001/`。`sub`、`ses` 同 LSL；`mod` 为模块（不沿用 LSL 的 `task`，以免与组别混淆）；`run` 为同一被试同一模块进入的第几次，崩溃后重进为 `run-002`，不覆盖前一次。
- 文件夹内：`session.csv`、`spacetime.csv`、`tap.csv`、`backstep.csv`、`look.csv`、`world_event.csv`、`tech_glitch.csv`。练习场只有 `session.csv`。
- 开发用调试日志放在 `NBI_Data/Debug/`，不进入分析。

**格式与写盘（已定）**

- 逗号分隔的 CSV，第一行为变量名；变量名与取值均为英文；缺失值留空；是否类用 `TRUE` / `FALSE`。
- 小数位：时间 3 位，坐标与距离 2 位，角度 1 位。
- 每写一行立即存盘，不在内存中积攒；APP 崩溃时崩溃前的数据仍在。
- 每张表按时间先后写；`touch_id` 在一个文件夹内从 1 开始递增。

**起止（已定）**

- `t_session` 的 0 点：场景加载完成、被试可以开始操作的那一刻（不是点主菜单按钮的那一刻，中间有加载时间）。`t_device_start` 记同一时刻。
- 停止记录：三指返回菜单离开模块时，写入 `t_device_end` 并关闭所有文件。APP 崩溃时没有结束时刻，缺少 `t_device_end` 即崩溃标记。

**改代码时再定的参数**：环视表"开始转""停稳"的阈值；`tech_glitch` 卡住的记录阈值（暂定 0.5 秒）。

**相关事项**：购买 Apple 开发者账户（免费签名 7 天后 APP 无法打开；数据仍在，覆盖安装可恢复）。

## 九b、练习场

**原理**：练习场中被试走光点引导的必走路线、按指定停靠点练触摸，实验员随时指导。此时的点击、失败、用时主要反映指导多少和练习设计本身，不代表被试的个人操作习惯，不能作为行为基线。练习场真正需要的只有练习时长（两组都练，作协变量或检查两组是否相当），它可由会话信息中 `module = Practice` 的起止时刻相减得到。

**做法**：练习场不设实验数据表，只写会话信息。现有练习流程日志（阶段切换时刻）保留为开发用调试日志，不进入正式分析。

## 九c、技术故障

**原理**：只记会让一段数据失效的 APP 运行异常，不做性能分析（帧率曲线、内存、渲染耗时等一概不记）。

- APP 能记的两种：切到后台或被打断（这段时间被试没在看场景，心率也不再对应虚拟自然）；画面严重卡住（被试看到定格画面，点击无反应，可能被误判为走不过去）。
- 不用专门记、能从现有数据看出的：APP 崩溃或被系统杀掉（会话信息缺少 `t_device_end`，各表在某一时刻戛然而止）；误触三指手势提前退回菜单（会话时长明显不足）。
- APP 记不到、靠实验员记录的：iPad 掉落、被试中途离开、实验员出手帮忙、被试不适、外界干扰等，写在实验记录单的"异常情况"一栏（发生了什么、约第几分钟）。

**做法**：单独一张小表 `tech_glitch`，见附A。现在这两种情况挂在声音日志里（`focus-lost`/`focus-back`、`hitch`），改代码时挪出来。卡住的记录阈值暂定 0.5 秒。

## 附A、变量清单（2026-10-22 确认）

命名规则：变量名与 level 一律用英文；变量名小写加下划线，level 首字母大写。level 不用 `None`：pandas 等工具默认把它读成缺失值，因此没打中写 `NoHit`，未受阻写 `NotBlocked`。时间单位秒（三位小数），坐标与距离单位米（两位小数），角度单位度。时间名与 PhysicoBridge 保持一致：`t_device` 为设备系统时间（Unix 秒，与 PolarBridge 数据包中的 `t_device` 同义），`t_session` 为会话内时间。

**通用时间列**：`t_session`、`t_device`。

**1. 时空表 `spacetime`**（每 0.1 秒一行，无分类变量）

| 变量 | 含义 |
|---|---|
| `t_session`, `t_device` | 时间 |
| `cam_x`, `cam_y`, `cam_z` | 相机位置 |
| `ground_y` | 脚下地面高度 |
| `view_yaw` | 画面左右朝向，0–360°，0° = 世界 +Z 方向，顺时针增加 |
| `view_pitch` | 画面俯仰，抬头为正、低头为负（Unity 内部低头为正，记录时取反） |

**2. 点击表 `tap`**（一次点击一行）

| 变量 | 含义 | level |
|---|---|---|
| `touch_id` | 触屏序号，各操作表共用 | — |
| `t_session`, `t_device` | 点击判定时刻 | — |
| `cam_x`, `cam_y`, `cam_z` | 点击时被试位置 | — |
| `intent` | 判定（沿用代码命名，没打中写 `NoHit`） | `NoHit` / `WalkTo` / `LookAt` |

| `block_type`, `block_reason` | 同点击表 | 同点击表 |
