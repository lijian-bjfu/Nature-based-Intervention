# 场景阴影设置、检查与性能优化规范

本文档用于统一当前自然场景的阴影设置、故障检查、移动端优化与验收流程。目标设备为较低版本 A 系列芯片的 iPad，目标帧率为稳定 30 fps；因此，阴影设计必须同时满足以下三项要求：

1. 玩家近处的重要物体具有清晰、稳定的接触关系和空间层次。
2. 大量细小植被不得无差别地参与实时阴影渲染。
3. 所有画质调整必须在目标 iPad 上验证，不能以电脑端帧率作为性能结论。

## 1 阴影设置的生效层级

阴影由多个层级共同决定，检查时应按以下顺序由上到下进行：

1. **当前 Build Target 与 Quality Level**：决定实际使用哪一个 URP Asset。
2. **URP Asset**：决定主光阴影分辨率、最大距离、级联数量、软阴影和附加灯阴影等全局能力。
3. **Renderer Asset**：决定 SSAO、屏幕空间效果及具体渲染路径。
4. **场景灯光**：决定某个 Light 是否投影，以及 Strength、Bias、Normal Bias 等参数。
5. **Camera 与 Scene/Game View**：决定实际观察位置、视野、LOD 切换及可见阴影范围。
6. **物体 Renderer 与 LODGroup**：决定每个模型及每一级 LOD 是否进入 ShadowCaster Pass。
7. **材质、Shader 与纹理**：决定 Alpha Clipping、双面渲染、叶片轮廓和 ShadowCaster Pass 是否正确。
8. **Terrain、Terrain Detail 与散布系统**：决定大量草木的绘制距离、密度、实例化和阴影数量。

只要其中任何一级关闭或排除了阴影，后续级别即使设置正确，也不会得到预期结果。

### 当前工程的管线判断

- 当激活的 Build Target 为 iOS，且 iOS 使用 `Mobile` Quality Level 时，Scene View 与 Game View 使用 `Mobile_RPAsset`。
- `Graphics Settings` 中的默认 Render Pipeline Asset 只有在当前 Quality Level 没有指定自己的 URP Asset 时才作为后备。
- Scene View 可以用于快速预览移动端 URP 的视觉效果，但 Scene Camera 与正式 Game Camera 不同；最终构图应在 Game View 检查，最终性能必须在真实 iPad 检查。

## 2 URP Asset：项目级阴影设置

当前移动端设置入口：`Assets/Settings/Mobile_RPAsset`。

| 设置 | 调高或开启后的画面影响 | 调低或关闭后的画面影响 | 性能影响 | 低端 iPad 建议 |
|---|---|---|---|---|
| Main Light / Cast Shadows | 主方向光产生实时阴影 | 全场景不再产生主光实时阴影 | 高；关闭可明显节省阴影渲染 | 开启 |
| Main Light / Shadow Resolution | 阴影轮廓更细，细叶更容易保留 | 锯齿增加，细小阴影可能消失 | 高；1024 提升到 2048 会使阴影图像素数变为 4 倍 | **2048（已定案，见第 14 节真机验证）** |
| Shadows / Max Distance | 更远处仍显示阴影，但单位面积精度下降 | 阴影更早消失，但近处更清楚 | 高；降低距离会减少进入阴影 Pass 的物体 | **30 m（已定案）。此值由近景画质决定，非性能约束** |
| Cascade Count | 近、中、远距离可分别分配阴影精度 | 大范围内阴影更粗 | 高；增加级联会增加阴影绘制工作 | 保持 2，不建议低端设备使用 4 |
| Cascade Split | 增大第一段会让近级联覆盖更远，但降低脚边精度 | 缩小第一段可提高近景精度，但中远景更粗 | 总成本变化通常较小，物体分配会变化 | 约 0.2～0.3 |
| Last Border | 最远端阴影淡出更平滑 | 淡出更突然 | 很低 | 保持默认 |
| Depth Bias | 减少 Shadow Acne，但阴影可能与物体分离 | 阴影更贴近物体，但可能产生黑点和条纹 | 几乎无性能差异 | 建议从 0.02～0.05 测试 |
| Normal Bias | 减少斜面自阴影错误，但细叶阴影可能被推开或消失 | 细小阴影更贴近投影物，但更容易出现表面条纹 | 几乎无性能差异 | 建议从 0.1～0.2 测试 |
| Soft Shadows | 阴影边缘柔和，可掩盖部分锯齿 | 阴影更硬、更清晰 | 移动端代价较高，且可能抹掉细草阴影 | 低端 iPad 关闭 |
| Soft Shadow Quality | 软阴影更平滑 | 软阴影更粗糙 | 采样数增加会提高 GPU 成本 | 不使用软阴影时无需调整 |
| Additional Light Shadows | 点光和聚光灯也能投影 | 只有主方向光投影 | 高；点光源阴影尤其昂贵 | 保持关闭 |
| Additional Lights Per Object | 同一物体可受更多灯光影响 | 同时参与计算的灯光更少 | 中等 | 室外场景尽量控制在 1～2 |

### 推荐的调整优先级

1. 先缩短 `Max Distance`。
2. 再调整 `Normal Bias` 和 `Depth Bias`。
3. 再优化 Cascade Split。
4. 最后才提高 Shadow Resolution。

降低 Max Distance 是少数能够同时提高近景阴影精度并降低性能成本的设置，应优先于提高分辨率。

## 3 Quality Settings：管线、LOD、纹理与 Terrain 质量

入口：`Edit > Project Settings > Quality > Mobile`。

在 URP 中，旧版 Quality 面板里的 Shadow Distance、Shadow Resolution 等字段不作为主要调整入口；应修改当前 Quality Level 指定的 URP Asset。Quality Settings 仍会影响管线选择、LOD、纹理 Mipmap 和 Terrain 质量。

| 设置 | 调高后的画面影响 | 调低后的画面影响 | 性能影响 | 建议 |
|---|---|---|---|---|
| LOD Bias | 高精度 LOD 保留到更远距离，模型和阴影更细 | 更早切换低精度 LOD | 中～高 | 保持 1；性能不足时测试 0.7～0.9 |
| Maximum LOD Level | 数值增加会跳过高精度 LOD | 0 允许使用 LOD0 | 可明显减少几何成本，但损失近景质量 | 当前保持 0 |
| LOD Cross Fade | LOD 切换更平滑 | 可能出现突然跳变 | 低端移动端会增加 Alpha Test 与过绘 | Mobile 保持关闭 |
| Global Mipmap Limit | 数值越大，实际纹理分辨率越低，细叶 Alpha 容易丢失 | 越接近 0，纹理越清晰 | 显存与带宽影响明显 | 全局可保持较低质量，重要植被使用单独 Mipmap Limit Group |
| Terrain Detail Distance | 更远处仍绘制草和细节 | 细节更早消失 | 高，尤其细节参与阴影时 | 建议约 50～80 m，按镜头需要测试 |
| Terrain Detail Density | 草木分布更密 | 草木更稀疏 | 高 | 应按设备能力分档 |

### Alpha Cutout 植被与 Mipmap 的特殊风险

当 Global Mipmap Limit 较高时，叶片透明通道会在低 Mip 中被平均。细叶可能变细或完全消失，ShadowCaster Pass 使用同一纹理时，阴影轮廓也会随之丢失。

推荐做法：

- 保持全局纹理限制以控制移动端显存。
- 给重要植被的 Base Map 建立独立 Mipmap Limit Group。
- 在纹理 Import Settings 中启用 `Mip Maps > Preserve Coverage`。
- Preserve Coverage 的 Alpha Cutoff Reference 应与材质的 Alpha Threshold 大致一致。

## 4 场景主灯光设置

入口：选择场景中的主 Directional Light，展开 `Light > Shadows`。

| 设置 | 画面影响 | 性能影响 | 建议 |
|---|---|---|---|
| Shadow Type / None | 完全不产生该灯光的阴影 | 可真正节省阴影 Pass | 仅用于不需要投影的灯 |
| Shadow Type / Hard | 清晰硬边阴影 | 比软阴影低 | 移动端主光推荐 |
| Shadow Type / Soft | 边缘柔和，但细小阴影可能被模糊 | 移动端 GPU 成本明显增加 | 低端 iPad 不建议 |
| Strength | 调高使阴影更黑，调低使阴影更浅 | 基本不改变阴影图生成成本 | 推荐 0.8～1；需要省性能时不能只把它设为 0 |
| Depth Bias | 调高可减少表面黑点，但会产生悬浮感 | 基本无性能差异 | 建议 0.02～0.05 |
| Normal Bias | 调高可减少斜面错误，但会吃掉细小接触阴影 | 基本无性能差异 | 当前场景可从 0.15 开始测试 |
| Near Plane | 太大时可能裁掉近处投影物；太小可能降低稳定性 | 通常很低 | 建议约 0.1～0.2 |
| Culling Mask | 决定哪些 GameObject Layer 受该灯光影响 | 排除大量对象可节省成本，但对象也不会受光 | 一般保持；不要误用来单独关阴影 |
| Rendering/Shadow Layer Mask | 决定哪些 Rendering Layer 被照亮或参与阴影 | 可用于按类别排除阴影 | Renderer 与主光至少要有一个共同 Layer 位 |

### 环境光对“阴影明显程度”的影响

如果 Shadow Strength 已经为 1，但阴影视觉上仍然很浅，应检查：

- Environment Lighting / Ambient Intensity 是否过高。
- 天空盒是否提供了过强的环境光。
- 植被材质的透光、半透明或背光参数是否过强。
- 后处理或颜色分级是否抬高了暗部。

这些设置会改变阴影对比度，但不会让缺失的 ShadowCaster 重新出现。

## 5 Mesh Renderer：单个物体的阴影规则

| 设置 | 含义与画面影响 | 性能影响 | 建议 |
|---|---|---|---|
| Cast Shadows / Off | 不向其他表面投影 | 最省 | 小草、碎叶、远处 LOD |
| Cast Shadows / On | 按正常剔除规则投影 | 物体会进入相关级联的 ShadowCaster Pass | 一般树木、岩石、灌木及近景 LOD |
| Cast Shadows / Two Sided | 正反面都参与阴影，适合薄片叶片 | 不一定增加 Draw Call，但会增加阴影图中的栅格化和过绘 | 只给确认存在背面投影问题的近景重要物体 |
| Cast Shadows / Shadows Only | 自身不可见，只显示阴影 | 仍有阴影成本 | 可用于低面数阴影代理网格 |
| Receive Shadows | 决定物体自身是否接收其他物体的阴影 | 主渲染 Pass 需要阴影采样 | 植被通常保持开启；它不控制该物体是否向地面投影 |
| Static Shadow Caster | 告诉支持缓存阴影的管线该投影物可视为静态 | 只有管线真正实现缓存时才可能获益 | 有风动画的植物保持关闭 |
| Contribute Global Illumination | 把物体纳入烘焙 GI 或 Lightmap | 增加烘焙时间、Lightmap 数据和管理成本 | 摇摆植被关闭；大型静态建筑、岩石按需开启 |
| Light Probes / Blend Probes | 从附近探针获取间接环境光 | 通常低于给大量植物烘焙 Lightmap 的成本 | 普通动态或风动植被保持开启 |
| Anchor Override | 指定 Light Probe 的采样位置 | 很低 | 默认 None；只有跨多个 Renderer 出现照明断层时设置共同锚点 |
| Motion Vectors / Per Object Motion | 为 TAA、运动模糊等记录物体运动 | 系统需要运动向量时可能增加额外处理 | 不使用 TAA、运动模糊时改为 Camera Motion Only |
| Dynamic Occlusion | 允许对象被遮挡剔除 | 通常有利于性能 | 保持开启 |
| Rendering Layer Mask | 决定对象与哪些灯光层交互 | 本身影响较小 | 默认 Layer 必须与主光匹配 |

## 6 LODGroup：按距离控制阴影成本

所有带 LODGroup 的模型都必须逐级检查 Mesh Renderer，不能只检查 Prefab 根节点。每一级 LOD 都有独立的 Cast Shadows 设置。

移动端植被的推荐原则：

| LOD | 推荐阴影策略 |
|---|---|
| LOD0 | 近景重要模型使用 On；只有确认薄片背面不投影时才使用 Two Sided |
| LOD1 | 一般使用 On |
| LOD2 | 小型植物通常关闭；大型树木可继续使用简化阴影 |
| LOD3 / Billboard | 小型植物关闭；远处大型轮廓按实际需要决定 |
| Culled | 模型与阴影都应停止绘制 |

以 `Wild_fern_Var4` 为例，它只是 LOD 阴影策略的一个样例，而不是全场景统一模板：可让 LOD0 使用 On 或 Two Sided、LOD1 使用 On、LOD2 与 LOD3 使用 Off。大型树木应根据其远距离轮廓价值采用不同策略。

### 阴影代理网格

对于外形复杂但阴影不需要逐叶精确的模型，可以使用：

- 可见精细网格：`Cast Shadows = Off`。
- 低面数代理网格：`Cast Shadows = Shadows Only`。

代理网格只需保留主要体块和轮廓，可以显著减少 ShadowCaster Pass 的三角形与 Alpha Clipping 过绘。

## 7 材质、Shader 与纹理检查

Alpha Cutout 植被推荐使用：

- `Surface Type = Opaque`。
- `Alpha Clipping = On`。
- 正确设置 Alpha Threshold。
- Shader 必须包含 `ShadowCaster` Pass。
- ShadowCaster Pass 必须执行与主渲染一致的 Alpha Clip。
- 若有风动画，ShadowCaster Pass 也必须执行相同或近似的顶点位移。
- 材质和 Shader 支持时启用 GPU Instancing。

| 设置 | 调整后的画面影响 | 性能影响 | 建议 |
|---|---|---|---|
| Alpha Threshold 降低 | 叶片和阴影更丰满 | 更多像素通过 Alpha Test，过绘略增 | 可从 0.5 测试到 0.4～0.45 |
| Alpha Threshold 提高 | 叶片变细，阴影容易断裂或消失 | 通过测试的像素减少 | 不应仅为性能盲目提高 |
| Render Face / Both | 正反面都显示 | 主渲染过绘增加 | 仅薄片植被使用 |
| GPU Instancing | 不直接改变画质 | 可降低大量相同 Mesh/Material 的 CPU 提交成本 | 保持开启；避免无意义的材质实例和关键字差异 |
| ShadowCaster Pass 缺失 | 物体可见但完全不投影 | 少了阴影成本，但画面错误 | 必须修复 Shader 或更换材质 |
| ShadowCaster 未执行风动画 | 影子与叶片摆动不一致 | 顶点计算略低但画面错误 | 应保持主 Pass 与 ShadowCaster 一致 |

Transparent 材质不适合作为常规草木卡片方案。移动端植被应优先使用 Opaque + Alpha Clipping，以获得稳定的深度、LOD、实例化与阴影行为。

## 8 Terrain、Terrain Detail 与散布系统

Terrain 本体的 Shadow Casting Mode 主要控制地形高度场是否投影，不代表所有 Terrain Detail 都自动获得正确阴影。

检查项目：

1. Terrain 是否开启 Draw Trees and Foliage。
2. Detail Distance 与 Detail Density 是否符合移动端目标。
3. Detail 是否使用 GPU Instancing。
4. Detail Prefab 材质是否具有 ShadowCaster Pass。
5. 小草是否有必要参与实时阴影。
6. Terrain、Detail、主光的 Layer 与 Rendering Layer Mask 是否匹配。

推荐分类：

- 大树、主要岩石和明显改变空间结构的灌木：允许实时阴影。
- 玩家近处的中型蕨类：仅近景 LOD 允许实时阴影。
- 小草、碎叶和高密度地表细节：关闭实时投影。
- 小草的接触感使用材质根部变暗、顶点色 AO、地表颜色变化或适度 SSAO 代替逐叶实时阴影。

## D.9 SSAO：作为小型植物接触感的补充

SSAO 不能产生具有太阳方向的长阴影，但可以让植物根部、岩石缝隙和地面接触位置变暗。对于数量巨大的小草，它通常比逐株实时阴影更合适。

当前 Mobile Renderer 已启用 SSAO。调整原则：

| 设置 | 画面影响 | 性能影响 | 建议 |
|---|---|---|---|
| Intensity | 提高会增强接触暗部 | 在算法、采样数不变时成本变化很小 | 可从 0.15 测试到约 0.25 |
| Radius | 增大影响范围，过大产生脏边或光晕 | 变化通常小于增加采样数 | 植被接触建议约 0.25～0.4 |
| Samples | 增加可减少噪点 | GPU 成本上升 | 低端设备优先 1～2 |
| Blur Quality | 提高会让结果更平滑 | GPU 成本上升 | 性能不足时优先降低 |
| Downsample | 开启后分辨率较低 | 可明显降低成本，但细节变粗 | 移动端保持开启 |

SSAO 自身也是全屏效果，不能视为免费。应比较“低质量 SSAO + 小草无实时阴影”和“关闭 SSAO + 大量小草实时阴影”两套方案在目标设备上的实际耗时。

## 10 标准阴影故障检查流程

当出现“物体可见但没有投影”时，按以下顺序检查，禁止一开始就提高全局阴影分辨率：

### 第一步：确认使用的渲染配置

1. 确认当前 Build Target。
2. 确认该平台当前 Quality Level。
3. 确认 Quality Level 指向的 URP Asset。
4. 确认 Scene View 的 Lighting、Effects 与 Post Processing 预览处于预期状态。

### 第二步：确认全局阴影能力

1. URP Asset 的 Main Light Cast Shadows 是否开启。
2. Shadow Distance 是否覆盖当前相机到物体的距离。
3. Shadow Resolution 与 Cascade Count 是否合理。
4. 主光 Shadow Type 是否不是 None。

### 第三步：确认对象是否进入阴影 Pass

1. 选择实际 Mesh Renderer，而不是只选择 Prefab 根节点。
2. 检查 Cast Shadows 是否为 On 或 Two Sided。
3. 如果有 LODGroup，逐级检查每一个 LOD Renderer。
4. 检查 GameObject Layer、Rendering Layer Mask 和主光 Mask 是否匹配。
5. 使用 Frame Debugger 检查对象是否出现在 `MainLightShadowCasterPass`。

### 第四步：确认材质和 Shader

1. 临时换成标准 URP/Lit、Opaque、Alpha Clipping 材质。
2. 若替换后出现阴影，则问题位于原 Shader 或材质。
3. 检查 ShadowCaster Pass、Cull Mode、Alpha Threshold 和风动画顶点位移。
4. 检查 Base Map 的 Mipmap、Preserve Coverage 与平台压缩结果。

### 第五步：判断是否为精度问题

仅用于诊断，可临时执行：

1. 将 Shadow Distance 降到 20～30 m。
2. 将 Normal Bias 降到约 0.05～0.1。
3. 将 Depth Bias 降到约 0.01～0.03。
4. 暂时提高 Shadow Resolution。
5. 暂时关闭 Soft Shadows。

如果阴影出现，说明对象和 Shader 可以投影，问题位于阴影图精度、级联分配或 Bias。诊断结束后应恢复移动端目标配置，再寻找成本更低的平衡点。

## 11 低端 iPad 推荐基线

建议从以下配置开始，而不是一次性追求最高画质：

- 只保留一个主 Directional Light 实时投影。
- Main Light Shadow Resolution：**2048**。已完成真机性能与热降频验证（第 14 节），1024 不再作为本项目的推荐值。
- Shadow Max Distance：**30 m**。该值由近景植物细节的可辨度决定，不是性能妥协。
- Cascade Count：2。
- Cascade Split：约 0.25。
- Hard Shadows。
- Additional Light Shadows：关闭。
- Depth Bias：约 0.02～0.05。
- Normal Bias：约 0.1～0.2。
- 大树、岩石和主要灌木：Cast Shadows = On。
- 中型植被：只允许 LOD0、LOD1 投影。
- 小草和高密度地表细节：Cast Shadows = Off。
- Two Sided：只用于确认单面阴影不完整的近景重点物体。
- LOD Cross Fade：关闭。
- GPU Instancing：开启。
- 风动植被 Static Shadow Caster：关闭。
- 风动植被 Contribute GI：关闭，使用 Light Probes。
- 无 TAA、运动模糊需求时，植被 Motion Vectors 使用 Camera Motion Only。
- 适度使用 Downsample SSAO 提供接触感，禁止盲目提高 Samples 与 Blur Quality。

## 12 性能验证与验收

30 fps 的单帧预算约为 **33.3 ms**。

**⚠️ 一条必须先纠正的认识**：本项目并未设置 30 fps 上限。`TapMoveCamera_V2.cs` 的 `ConfigureDevice()` 里设的是 `targetFrameRate = 60`（注意 `vSyncCount` 在 iOS 上被忽略）。

iOS 的画面提交锁在屏幕刷新沿上，因此**帧率只能取 60 / 30 / 20 / 15 这几个离散值**。观察到"稳定 30 fps"的真实含义是：单帧耗时落在 16.7 ms 到 33.3 ms 之间的某处，具体多少无法从帧率读数得知。

**推论：帧率读数不是连续量，不能用于比较两个都显示 30 fps 的配置。**它只能用作阈值指示器——见第 14 节的"悬崖探测法"。

### LOD 阴影对照矩阵（备用手段，非必测）

> **状态更新（2026-08-08）**：2048 已通过真机验证且余量充足，本矩阵不再是必做项。它保留为**余量不足时的回收手段**——例如日后场景内容大幅增加、或换用更弱设备时。

若需执行，在目标 iPad 上依次测试：

1. 小型植被阴影全部关闭。
2. 仅小型植被 LOD0 开启阴影。
3. LOD0 与 LOD1 开启阴影。
4. 所有 LOD 开启阴影。
5. 在必要对象上将 On 改为 Two Sided。

每次只改变一个变量，并记录：

- 平均帧率与最低帧率。
- CPU Main Thread 时间。
- GPU Frame Time。
- `MainLightShadowCasterPass` 时间。
- Batches、SetPass Calls、Triangles。
- 运行 20 分钟后的温度和降频表现。

### 验收原则

- GPU 和 CPU 均应留有余量，不以刚好 33.3 ms 为合格线。
- 建议常态 GPU Frame Time 控制在约 25～28 ms 以内，为场景峰值和热降频留出空间。
- 阴影设置必须在正式 Game Camera 和目标 iPad 分辨率下检查。
- Scene View 用于视觉迭代，Game View 用于构图与 LOD 检查，真实 iPad 用于最终画面与性能结论。
- 若小植物阴影的视觉收益不明显，应优先关闭其阴影，而不是继续提高全局 Shadow Resolution。

## 13 本轮阴影调整实测记录与结论

### 测试背景

本轮测试在电脑端 Unity Editor 的 Scene View 中完成。当前 Build Target 为 iOS，Quality Level 使用 `Mobile`，因此 Scene View 使用的是 `Mobile_RPAsset`。本轮结论可以作为移动端画面调整的直接参考，但所有性能结论仍需在真实 iPad 上验证。

本轮测试的核心问题是：在当前森林场景中，哪些设置对细小植物阴影和整体空间层次的视觉影响最大。

### 实测影响排序

按本轮 Scene View 中观察到的视觉变化，从强到弱排序如下：

1. **Shadow Resolution**。
2. **Shadow Depth Bias**。
3. **Shadow Max Distance**。
4. **Preserve Coverage 与 Alpha/Mipmap 相关设置**。
5. **主灯光 Inspector 中除 Bias 外的其他阴影参数**。

这个排序是当前场景的实测结果，不应被当作所有项目都完全相同的固定顺序。它说明当前场景的主要瓶颈是 Shadow Map 的空间精度，而不是材质本身缺少投影能力。

### 1. Shadow Resolution：本轮影响最大的设置

实测将主光 Shadow Resolution 从 1024 提升到 2048 后，整个画面出现了明显改善：

- 1024 下的阴影呈现破碎、断裂和层次不足。
- 细叶、小草、蕨类等小型轮廓很难在 Shadow Map 中留下连续结果。
- 2048 下阴影轮廓明显更稳定，地面层次、植物与岩石之间的空间关系更清楚。
- 小型植被不一定得到精确的逐叶阴影，但能够形成视觉上可信的小块阴影。

技术解释：1024 提升到 2048 后，阴影图每个方向的像素数翻倍，总像素数变为 4 倍。原本不足一个 Shadow Texel 的细叶轮廓，获得了更多被记录的机会。因此，对于当前包含大量细碎自然轮廓的场景，Shadow Resolution 是最直接的全局画质参数。

性能判断：2048 会增加 Shadow Map 的显存、带宽和栅格化压力，特别是场景中有大量 Alpha Clipping 植被时。

> **已于 2026-08-08 完成真机验证：2048 在目标设备上余量充足，已定案采用。**验证过程与数据见第 14 节。

### 2. Shadow Depth Bias：本轮第二明显的设置

实测将 Shadow Depth Bias 从 0.1 降低到 0.02 后：

- 阴影更贴近叶片、枝条和植物根部。
- 原本没有明显投影的细叶下方开始出现小块接触阴影。
- 阴影形状未必准确，但从正常观察距离看已经足以建立空间层次。
- 该设置几乎不增加 GPU 渲染成本，因此具有很高的画质收益与性能比。

技术解释：原来的 0.1 对贴近地面的薄叶片偏大，阴影被向外推开后，小于 Shadow Texel 的阴影容易彻底脱离投影物或被过滤掉。降低 Bias 后，即使阴影只能表现成一小团，也能提供“植物确实落在地面上”的视觉信息。

风险与后续检查：

- 地面、石头和缓坡表面是否出现 Shadow Acne。
- 摄像机移动时是否出现黑点、条纹或闪烁。
- 日照方向较低时是否出现明显自阴影错误。
- 阴影级联边界附近是否出现跳动。

若 0.02 在真机或其他光照角度下产生明显伪影，应依次测试 0.03、0.04 和 0.05，选择不产生明显 Shadow Acne 的最低值。

### 3. Shadow Max Distance：近景质量与性能的共同调节器

实测缩短 Shadow Max Distance 后：

- 近处小草、细叶和小型植物的阴影明显变清楚。
- 同一 Shadow Resolution 被集中到更小的世界范围，近景 Shadow Texel 密度提高。
- 远距离投影物更早退出 ShadowCaster Pass，因此理论上可以回收部分 GPU 和 CPU 成本。

Depth Bias 与 Max Distance 的组合效果尤其明显：较低的 Bias 让阴影贴近植物，较短的阴影距离为近景分配更多 Shadow Texel，两者组合后，即使细小叶片无法形成精确轮廓，也能产生清楚、稳定且可接受的接触阴影。

这意味着当前场景不应只比较“1024 与 2048”，还应比较完整组合：

- 1024 + 较长 Max Distance。
- 1024 + 较短 Max Distance。
- 2048 + 较长 Max Distance。
- 2048 + 较短 Max Distance。

其中“2048 + 较短 Max Distance”可能是更适合当前场景的画质方案：提高分辨率带来清晰度，同时用较短距离减少远处投影物，回收一部分性能。

> **真机验证结果（第 14 节）**：该组合已确认可行，且实测表明**性能并非选择 Max Distance 的约束**——即使拉长到 60 m，冷机仍可达 60 fps。因此 30 m 这个值应完全按近景画质来定，不必为性能让步。

### 4. Global Mipmap Limit：主要改变纹理，不直接提高 Shadow Map 精度

本轮最初将 Global Mipmap Limit 从 Quarter 改为 Half 时，因为注意力集中在阴影，未立即发现明显变化。后续对照确认，变化主要发生在纹理层面：

- Quarter 下地面材质明显更模糊。
- Half 下地面纹理、颜色层次和表面细节更清楚。
- 该设置不会直接提高 Shadow Map Resolution，因此不会产生与 1024 → 2048 类似的阴影改善。

Half 到 Quarter 相当于纹理每个方向再缩小一半，最高级纹理的像素数约降到四分之一，因此能够节省显存和纹理带宽。它仍可能间接影响 Alpha Clipping 植被：ShadowCaster 会读取叶片纹理的 Alpha，若低 Mip 把细小透明轮廓平均掉，阴影也可能变细或消失。但在本轮场景中，这种影响明显弱于 Shadow Resolution、Bias 和 Max Distance。

当前结论：Global Mipmap Limit 属于纹理与显存优化问题，不纳入本轮阴影参数的主要调节链路。后续应使用按材质类型、纹理用途和观察距离分类的策略，而不是仅依赖全局 Half 或 Quarter。

### 5. Preserve Coverage：有效但属于辅助设置

开启 Preserve Coverage 后观察到一定改善，但影响没有 Shadow Resolution、Depth Bias 和 Max Distance 明显。

技术解释：Preserve Coverage 只在生成较低级 Mipmap 时，尽量维持通过 Alpha Cutoff 的像素覆盖面积。它可以减少远距离叶片逐渐变细、断裂或消失的问题，但它不会增加 Shadow Map 的空间分辨率，也不能补偿过大的 Bias。

因此，Preserve Coverage 应作为 Alpha Cutout 植被的稳定性规范保留，但不能被当作提升整体阴影质量的主要手段。

### 6. 主灯光其他阴影设置：本轮影响较小

本轮调整中，主灯光 Inspector 内除 Bias 外的其他阴影设置，对画面改善相对有限。这一结果与当前配置相符：

- Shadow Strength 已经接近或达到 1，继续提高没有空间。
- 主光 Shadow Resolution 和 Max Distance 由当前 URP Asset 控制。
- Mobile URP 中 Soft Shadows 已关闭。
- Near Plane 主要用于解决特定裁剪或精度问题，不是当前细叶阴影缺失的主要原因。

因此，主灯光 Inspector 更适合调整阴影对比度和局部伪影；当前场景的全局阴影清晰度，仍应优先从 URP Asset 的 Resolution、Distance 和有效 Bias 入手。

### 本轮阶段性结论

1. 当前场景的细小植被阴影首先受 Shadow Map 空间精度限制。
2. 2048 带来的画质提升明确且显著，**且已完成真机性能验证并定案**（第 14 节）。
3. Depth Bias 从 0.1 降到 0.02，具有非常高的视觉收益与性能比。
4. 缩短 Max Distance 可同时改善近景阴影精度并减少远处投影物。
5. 对远处小植物，不需要追求准确的逐叶阴影；稳定的小块接触阴影已经能够提供足够的空间层次。
6. Global Mipmap Limit 主要属于纹理清晰度和显存管理，不应与 Shadow Resolution 混为一类。
7. Preserve Coverage 是 Alpha Cutout 植被的辅助稳定措施，而不是主要阴影清晰度参数。

## 14 真机性能验证与定案（2026-08-08）

第 13 节的画质结论来自电脑端 Scene View，性能结论当时悬而未决。本节记录在目标 iPad 上完成的验证，**阴影参数至此定案**。

### 14.1 待回答的问题

将主光 Shadow Resolution 从 1024 提升到 2048（阴影图总像素数变为 4 倍），目标设备能否承受？

### 14.2 ⚠️ 两条工具弯路（记下来，不要再走一遍）

**弯路一：Memory Profiler 回答不了这个问题。**

最初试图用 Unity Memory Profiler 抓真机快照来评估 2048 的代价，抓取过程冻结 iPad 十余分钟无结果。

事后判断：**这个工具从一开始就用错了，即使抓成功也没有价值。**

阴影图是一张深度纹理，边长即该设置值。1024² 约 2～4 MB，2048² 约 8～16 MB，**增量在 6～12 MB 量级**。而当时 Total Resident 约 0.93 GB、上限 2.87 GB——增量占当前占用约 1%，**低于两次快照之间的自然波动**，无法与噪声区分。

> **原则：能笔算出量级的东西，不要去测。**Shadow Resolution 的代价在 GPU 时间（毫秒），不在内存（兆字节）。

（关于那次卡死本身：判断方法是看 Unity 工程根目录下的 `MemoryCaptures/`，`temp.tmpsnap` 若大小与时间戳连续多次 `ls` 都不变，即已断开，等下去无意义。历史成功快照为 33～110 MB，可作为参照。另需注意 Memory Profiler 与 Profiler 两个窗口的连接目标下拉**各自独立**，都必须手动从 Editor 切到设备。）

**弯路二：Unity Profiler 的 GPU 模块在 Metal 下不可用。**

GPU Usage 模块始终为空，悬停警告图标提示：

```
GPU Profiling is currently not supported when using Metal
```

**这句话的主语是 Unity 的 GPU Profiler 模块，不是设备。**Metal 是苹果唯一的图形 API，设备当然支持。这意味着 **Unity Profiler 永远无法给出本项目的 GPU 毫秒数**，换设备也无效。`MainLightShadowCasterPass` 的耗时若确实需要，只能走 Xcode 的 Metal GPU Capture 或 Instruments 的 Metal System Trace。

### 14.3 Unity Profiler 的有效产出：排除 CPU

GPU 模块虽不可用，CPU 模块正常。植被最密处单帧 Hierarchy：

| 条目 | 耗时 | 占比 |
|---|---|---|
| `PlayerLoop` | 33.38 ms | 整帧 |
| └ `WaitForTargetFPS` | **27.60 ms** | 82.6% |
| └ `PostLateUpdate.FinishFrameRendering` | 4.92 ms | 14.7% |

**CPU 实际工作量仅约 5.8 ms，其余 27.6 ms 在空等。**

两条推论：

1. **CPU 不是瓶颈，余量约 5 倍。**33 ms 的帧长只能由 GPU 撑起，阴影方向的调查是对的。
2. **Xcode Debug Navigator 显示的"CPU 80%"是假象**——空等同样占用 CPU 时间片。该读数不能用于判断 CPU 负载。
3. 附带结论：工程规范文档 6.1 记录的树实例化警告（每棵树一次 draw call）属 CPU 侧负担，**在当前 CPU 余量下不构成瓶颈，可暂不处理**。

### 14.4 悬崖探测法：绕过帧率量化的判断手段

由于帧率被量化为 60/30/20（原因见第 12 节），"两个配置都显示 30 fps"无法说明二者是否有差距——实际耗时可能是 20 ms，也可能是 32 ms。

**方法：不去测量连续值，而是故意施加一份已知的额外负担，观察是否掉档。**

答案藏在"掉不掉"这一个二元事件里，不需要任何数值读数，也不需要图形学知识。

### 14.5 实测记录

设备：iPad Pro 11" 一代（2018, A12X, 4 GB），iPadOS 26.4.2。均为 Development Build、有线连接、Profiler 连接中——**条件比正式实验更苛刻**。

**测试 A — 目标配置耐久**

配置：Shadow Resolution 2048 / Global Mipmap **Half** / Max Distance 30

| 观测项 | 结果 |
|---|---|
| 运行时长 | 约 15～16 分钟连续 |
| 帧率 | **全程稳定 30 fps，无掉档** |
| 机身温度 | 温，约 37～38 °C，不烫手 |
| 操作手感 | 流畅，与上一版无本质差别 |
| Debug Navigator 内存 | 约 1.46～1.5 GB（Development Build，**不可与正式 Build 的 0.93 GB 直接比较**） |

**测试 B — 加压探测**

配置：Shadow Resolution 2048 / Global Mipmap Half / Max Distance **60**（仅为施压，非采用值）

| 阶段 | 帧率 |
|---|---|
| 进入场景、冷机 | **60 fps** |
| iPad 温度上升后 | 30 fps，此后稳定 |

**测试 C — 阴影质量提升（级联、软阴影、Bias、DPI）**

测试 A/B 只解决了"2048 能不能跑"，未解决画质。本组针对锯齿与抖动。

**起点问题**：2048 定案后，近景阴影仍有明显锯齿，且移动时边缘爬行、闪烁。

**诊断中纠正的三条认识：**

1. **URP Asset 的 Soft Shadows 是总闸。**它关闭时，着色器不编译软阴影关键字，**各灯光自身的 Soft/Medium 设置一律空转**。此前主灯光设为 Medium 实为硬阴影渲染，这是锯齿的直接来源。
2. **MSAA 修不了阴影锯齿。**URP Asset 里的 2X/4X/8X 作用于几何轮廓边的光栅化；阴影边缘是阴影贴图的**采样结果**，不存在对应的多边形边界。开 MSAA 只掉帧率，锯齿不变。
3. **锯齿与抖动是两个问题。**锯齿 = 空间采样不足（硬阴影 + 渲染分辨率低）；抖动 = 时间不稳定（Bias 偏低导致斜面自阴影 + 风动植被 + 阴影图逐帧重新贴合）。分开治。

**变更一：Cascade Count 2 → 4（先行，单独测过）**

| 结果 | 值 |
|---|---|
| 近景阴影清晰度 | 显著提升 |
| 帧率 | 30 fps，无变化 |

原理：**URP 的阴影图集按 2×2 切分，因此 2 级与 4 级的单块 tile 都是 1024×1024。**从 2 级换到 4 级，单块像素数不变，但最近一块覆盖的世界范围从半径 15 m 缩到 6 m，texel 密度提高约 2.5 倍。代价仅为多跑两趟阴影绘制。

> 这推翻了第 2 节"低端设备保持 2 级"的旧建议——那条写于帧率 9 fps 时期，在当时的余量下成立，现已不成立。

**变更二：四项同时变更（软阴影 + Bias + DPI）**

| 项 | 原值 | 新值 |
|---|---|---|
| URP Asset Soft Shadows | Disabled | **Enabled, Low** |
| Normal Bias | 0.1 | **0.2** |
| Depth Bias | 0.02 | **0.03** |
| Target DPI | 150 | **180** |

| 观测项 | 结果 |
|---|---|
| 画面细节 | 明显更丰富、更清晰 |
| 阴影锯齿 | 大幅减少 |
| 帧率（空旷处） | 30 fps |
| 帧率（植被密处） | **25～26 fps** |
| 主观流畅度 | 25↔30 的切换感受不到，整体仍流畅 |

**⚠️ 归因未分离**：四项同时改，掉帧被归给 DPI 是基于预测而非测量。软阴影的 PCF 每像素多次采样阴影贴图，在满屏树影的场景中同样不便宜，其占比未知。若日后需要精确回收性能，应单独退回 DPI 150 重测以分离两者。

**Target DPI 的技术含义**（本轮补课）：

`Resolution Scaling Mode = Fixed DPI` 指定按给定像素密度渲染，再拉伸铺满屏幕。缩放比 = Target DPI ÷ 屏幕原生 DPI。iPad Pro 11" 原生 2388×1668、264 dpi：

| Target DPI | 缩放比 | 实际渲染 | 像素数占原生 |
|---|---|---|---|
| 150 | 0.568 | 1357 × 948 | 32% |
| **180（当前）** | 0.682 | **1628 × 1137** | **47%** |
| 264 | 1.0 | 2388 × 1668 | 100% |

150 → 180 使渲染像素数提高约 44%。**GPU 的每一项逐像素工作——着色、阴影采样、SSAO、后处理——都同比例变贵**，因此它比任何单独的阴影参数影响都大。屏幕最终仍显示 2388×1668，由硬件拉伸，代价是画面偏软。

**帧率量化的修正**：本机为 ProMotion 120 Hz 屏，量化台阶为 120/60/40/30/24/20，比第 12 节所述的 60 Hz 情形更细。观测到的 26 fps 是 30 与 24 混合的平均值，非连续量。

### 14.6 结论

**1. 2048 定案采用，且余量明确。**

测试 B 的冷机 60 fps 是本轮最有价值的一个数：**60 fps 意味着单帧耗时低于 16.7 ms**。这是第一次把此前的未知量框住——在最重的配置下（2048 + Half + Max Distance 60）、不降频时，帧预算仍有富余。

**2. 真正的限制是热降频，不是阴影分辨率。**

长期观察到的"稳定 30 fps"从来不是工作量的天花板，而是**降频后的地板**。同一配置冷机 60 / 热后 30，为工程规范文档 6.1 的判断提供了直接证据。

> **推论：继续在阴影参数上抠性能没有收益。**若需更高帧率，方向是散热与设备更换，不是继续降画质。

**3. Max Distance = 30 是纯画质决策。**

测试 B 证明拉长到 60 也不产生性能问题，因此不存在画质与性能的取舍，该值应完全按视觉效果定。

**4. 4 级级联是本轮性价比最高的一项改动。**

近景清晰度显著提升，帧率零代价。原因见 14.5 变更一。**遇到近景阴影不够清晰时，应先考虑增加级联数，而不是提高 Shadow Resolution**——前者提高 texel 密度且几乎免费，后者提高的是图集总量且成本按平方增长。

**5. 画质提升的代价：帧率从锁定 30 变为 25～30 波动。**

这是本轮唯一的负面变化。取舍依据是工程规范文档 3.6："糊的损失较小，还是同一个环境；平的损失更大，变成了另一个刺激。"分辨率与阴影清晰度属于前者，为其付出可接受的帧率代价是合理的；且实测主观上感受不到切换。

**⚠️ 未验证：该配置未跑过 20 分钟耐久测试。**此前 DPI 150 时余量厚，热降频不足以掉档；现在常温已在 25～30，降频后可能滑至 20 出头。**若日后耐久测试不达标，中间落点为 Target DPI 165**（像素数仅比 150 多 21%，约为 180 代价的一半），此值尚未试过。

**6. ⭐ 晕动风险已实测排除。**

研究者本人对晕动高度敏感（27 寸显示器上测试同一场景有明确不适；其他 3D 游戏两分钟内即恶心）。**在 iPad 上无论如何行走、转向，均无任何晕动感。**

这与第六部分登记的"讨论中的问题：iPad 平台是否影响晕动"直接相关，构成一条支持性证据：**小屏幕不占据周边视野，视觉—前庭冲突显著弱于大屏或 VR。**这是本项目选择 iPad 而非 VR 的一条事后支持理由。

> 该结论为单人观察，不能替代正式的被试筛查与单项量表测量，但**足以支持"不必为晕动风险牺牲画质或交互设计"这一工程决策**。

**7. 未系统覆盖的一项。**Depth Bias 从 0.1 与 0.03 目视对比差异不大，暂定 0.03。未在不同太阳角度下逐一检验 Shadow Acne。若日后调整光照方向，需重新目视确认。

### 14.8 给后续测试的方法学提示

1. **先问"这个工具能不能回答我的问题"，再打开它。**本轮两次弯路都源于跳过了这一步。判据是量纲——问题的答案以什么为单位（MB？ms？），工具就必须产出那个单位。
2. **能笔算的不要测。**
3. **A/B 必须在同一热状态下**，否则冷热差异会淹没被测变量。理想做法是同一次运行内切换（可在 Quality Settings 建两个等级各指一份 URP Asset，运行时用 `QualitySettings.SetQualityLevel()` 切，绑到调试框按钮上），既省出包，又消除热漂移。
4. **加压探测优于精确测量**，当你要的是"够不够"而不是"是多少"时。

## 15 下一阶段：场景纹理优化方向

纹理优化应作为下一轮独立实验进行，本阶段只记录研究方向，不在本轮阴影结论中展开具体参数。

后续建议方向：

1. 按用途分类纹理：Terrain、近景岩石、树木、灌木、草、远景资产、UI 与特殊 Mask。
2. 按观察距离和视觉重要性，为不同类别建立独立 Mipmap Limit Group，避免全局 Half 或 Quarter 一刀切。
3. 分别测试 iOS 平台的 Max Size、压缩格式、压缩质量和 Mipmap Streaming 对画质、显存和带宽的影响。
4. 对 Alpha Clipping 植被统一检查 Preserve Coverage、Alpha Cutoff Reference、材质 Threshold 和平台压缩后的 Alpha 轮廓。
5. 对 Terrain 和近景大面积材质重点检查 Quarter 下的模糊问题；对远景和低重要性资产优先保留更激进的降级。
6. 在真实 iPad 上同时记录纹理清晰度、运行内存、纹理显存、加载时间、GPU 带宽压力和长时间热降频表现。

该阶段应单独建立测试矩阵和实测记录，再根据结果形成正式的“场景纹理导入与平台覆盖规范”。
