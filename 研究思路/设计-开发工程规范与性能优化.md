# 第一部分：iOS 构建链路

## 1.1 概念框架（先理解这个，再看操作）

iOS 与其他平台不同。**Unity 不能直接生成能装到 iPad 上的 app**，它只能生成一个 Xcode 工程，剩下的编译、签名、安装由 Xcode 完成。

```
Unity 工程
   ↓ Build（Unity 生成）
Xcode 工程          ← 每次生成出来的中间产物，不是需要长期维护的东西
   ↓ 编译 + 签名（Xcode 完成）
iPad 上的 app
```

**关键原则：Unity 是源头，Xcode 是产物。要改设置就回 Unity 改。**

常见误解（本轮踩过）：
- ❌ 以为需要在 Xcode 里"新建一个 iOS 项目" —— **不需要，永远不要点 New Project**
- ❌ 以为 Bundle Identifier 要在 Xcode 里手抄一遍 —— **不需要，Unity 会自动写进去**
- ❌ 以为 Unity Build 完就结束了 —— **Xcode 那一段是必须的**

## 1.2 签名需要的三样东西

| | 回答什么问题 | 谁产生 | 在哪儿设 |
|---|---|---|---|
| **Bundle Identifier** | 这个 app **是谁** | 你起的名字 | Unity |
| **Team（Team ID）** | **谁**为它担保 | 你的 Apple ID | Unity（推荐）或 Xcode |
| **证书 + 描述文件** | 苹果**认不认**这个组合 | Xcode 自动向苹果申请 | 不用管 |

**⚠️ 注意：`Signing & Capabilities` 不是一个设置项，它是 Xcode 里显示上述内容的面板名字。**（本轮曾把它误当成第三个"注册物"。）

## 1.3 两类设置必须分清（这决定换电脑时要重做什么）

**跟着工程走**（存在 `ProjectSettings.asset` 里，拷到别的电脑还在）：
- Bundle Identifier
- Team ID
- 所有 Player Settings

**跟着这台电脑走**（存在 macOS 钥匙串和用户目录里，换电脑就没了）：
- Xcode 里的 Apple ID 账号
- 证书与描述文件
- Xcode 本身、命令行工具配置

> **推论：换电脑或重装系统之后，Unity 侧不用动，Xcode/macOS 侧全部重做一遍。**

本轮的处境正是这么来的：Unity 工程一直在（Bundle ID 还在），但存 iOS 工程的移动硬盘不在手边、这台机器上的证书状态也没有，所以电脑侧全部重来。

## 1.5 ⚠️ 第一个坑：xcode-select 指向错误

**症状**：Unity 或 Xcode 报告找不到 Xcode，或构建直接失败。

**检查**：终端里跑

```bash
xcode-select -p
```

- 正确输出：`/Applications/Xcode.app/Contents/Developer`
- 错误输出：`/Library/Developer/CommandLineTools` ← **系统认为你只装了命令行工具，没装 Xcode**

**修复**（需要管理员密码）：

```bash
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer
```

输密码时屏幕不显示任何字符，这是正常的，输完直接回车。

**这一条应作为环境检查的第一步**，它会让后面所有步骤莫名其妙地失败，而报错信息不会指向它。

## 1.6 Apple ID 与 Team ID：先有鸡还是先有蛋

### 添加 Apple ID

1. 打开 Xcode（首次打开可能要装附加组件、同意许可，都同意，等它跑完）
2. **Xcode → Settings**（`⌘ ,`）→ **Apple Accounts** 标签
3. 左下角 `+` → **Apple ID** → 登录
4. 成功后会出现「你的名字 (Personal Team)」，并显示 `On Device Testing / 10 Provisioned Devices`

### ⚠️ 第二个坑：此时还读不到 Team ID

**免费账号的证书是"第一次签名时才被创建"的。**账号刚加进去时本地还没有证书，Team ID 也就还不存在。

```bash
defaults read com.apple.dt.Xcode IDEProvisioningTeams
# 此时会返回 "does not exist"，这是正常的，不是出错
```

**这不是死结，绕法如下**（一次性成本）：

1. Unity 里先不填 Team ID，先出一次包
2. 在 Xcode 里**手动**勾选 `Automatically manage signing`、手选 Team
3. Run 成功 → **证书在这一刻被创建**
4. 从证书名里读出 Team ID
5. 回填进 Unity → **此后永久自动**

### 读取 Team ID 的三个途径

按可靠性排序：

```bash
# 途径一（Xcode 26 上可能读不到）
defaults read com.apple.dt.Xcode IDEProvisioningTeams

# 途径二（证书创建后可用）
security find-identity -v -p codesigning
# 输出形如：Apple Development: Jian Li (ULWYMLNC76)
```

**途径三**：Xcode → 目标 target → Signing & Capabilities → `Provisioning Profile` 后面的小 ⓘ → 弹出面板里的 `Signing Certificate: Apple Development: Jian Li (XXXXXXXXXX)`，括号里那十位。

> **注**：证书名括号里的严格讲是"证书持有人 ID"，只有在 Personal Team（个人团队）情况下它等于 Team ID。本项目属于这种情况。

**本项目的 Team ID：`ULWYMLNC76`**

### ⚠️ 多个 Apple ID 的陷阱

如果有多个 Apple ID，Team 下拉里会出现多个**显示名几乎相同**的条目（本项目出现过 `Jian Li` 和 `Jian li`，仅大小写之差）。选错的报错信息极难理解。

**建议在 Xcode → Settings → Apple Accounts 里删掉不用的账号**（选中点左下角 `−`），从源头消除歧义。

## 1.7 ⚠️ 第三个坑：Bundle Identifier

**免费 Apple ID 下，Bundle Identifier 必须在苹果全球范围内唯一。**

- 短名字（如 `com.jl.natureprobe`）极可能已被他人注册 → 报 `Failed to register bundle identifier`
- **报错不会说明是重名**，所以很难猜
- 解法：加入自己的唯一标识，如 `com.jianli0615.natureprobe`

**⚠️ 更隐蔽的限制：免费账号每 7 天最多注册 10 个 App ID。**反复改名试错会撞上限额，之后**改成什么都失败**——看起来像"怎么都不行"，其实只需要等。

> **本项目的 Bundle ID 是 `com.jianli0615.natureprobe`，已注册成功，不要再改。**

## 1.9 构建流程

### 第一次

1. **关掉 Xcode**
2. Unity → **File → Build Profiles** → 左边选 iOS → **Switch Platform**（首次会重新导入全部资源，很慢，可能几十分钟）
3. 右下角 **Build** → 选一个**空文件夹**
4. 等待（IL2CPP 要把 C# 编译成 C++ 再编译成机器码，十几分钟到半小时正常，**别中断**）
5. 打开生成的 `Unity-iPhone.xcodeproj`
6. **两个 target 都要处理**：`Unity-iPhone` 和 `UnityFramework`
   - Signing & Capabilities → 勾 `Automatically manage signing` → Team 选 Personal Team
   - **漏掉 UnityFramework 会在编译中途失败，且报错不提是哪个 target**
7. 顶部选择设备 → 点 ▶︎

### 以后每次

1. **关掉 Xcode**
2. Unity → Build → 同一个文件夹 → **Replace**
3. 打开 Xcode → 点 ▶︎

**为什么每次都要关 Xcode**：Xcode 开着会锁住文件、缓存索引，Unity 往同一文件夹写东西容易撞车，症状是"改了没生效"或莫名编译错误——代码明明是对的，最难查。

### ⚠️ 第四个坑：一律用 Replace，不要用 Append

Unity 在输出文件夹已有旧工程时会问 **Replace**（删掉重建）还是 **Append**（增量更新）。

**旧记录（第一阶段）里写的"选 Append"已作废。**那条经验来自空场景阶段，资源量小、不会暴露增量同步问题。场景变重之后，Append 会产生新旧文件混合，本轮因此损失了三轮时间。

**Append 造成的三个报错，看起来毫无关联，实际同一个原因：**

| 报错 | 阶段 |
|---|---|
| `Undefined symbol: _g_CodegenRegistration` | 链接 |
| `Build input file cannot be found: lib_burst_generated.cpp` | 编译 |
| `level0 is corrupted! [Position out of bounds!]` | 运行时加载场景 |

**Team ID 回填 Unity 之后，Replace 没有任何副作用**（签名会自动重新写入），代价只是编译久一点。

# 第二部分：故障速查表

| 症状 | 真实原因 | 解法 |
|---|---|---|
| Unity 找不到 Xcode / 构建直接失败 | `xcode-select` 指向 CommandLineTools | `sudo xcode-select -s /Applications/Xcode.app/Contents/Developer` |
| `defaults read ... does not exist` | 还没签过名，证书尚未创建 | 先手动签一次，再读 |
| Provisioning Profile 下拉只有 Import/Download，无可用项 | `Automatically manage signing` 没勾。**免费账号不能手动创建描述文件** | 勾上自动签名 |
| `Failed to register bundle identifier` | Bundle ID 全球重名，或撞上 7 天 10 个 App ID 限额 | 换更唯一的名字；若已撞限额只能等 |
| 编译中途失败，报错不提 target | `UnityFramework` 没设签名 | 两个 target 都要设 |
| `Insufficient storage` / `Failed to install the app` | iPad 存储不足 | 腾 5 GB 以上 |
| `EXC_RESOURCE (RESOURCE_TYPE_MEMORY: high watermark memory limit exceeded)` | 内存超限，被 iPadOS SIGKILL | 见第三部分 3.3 |
| app 启动闪退，无 C# 异常也无崩溃栈 | 同上。iPad `JetsamEvent` 日志会记 `reason: highwater` | 同上 |
| `Undefined symbol: _g_CodegenRegistration` | Append 增量不一致 | Replace |
| `Build input file cannot be found: lib_burst_generated.cpp` | 同上；换新文件夹也无效，因为缓存在 Unity 的 `Library` 里 | 稍微等一会让 Xcode Indexing 准备就绪。如果还不行关 Unity → 删 `Library/Bee`、`Library/BurstCache` → Replace 到新文件夹 |
| `level0 is corrupted! [Position out of bounds!]` | ①Append 残留 ②**MonoBehaviour 文件名≠类名** | 见下条 |
| **编辑器里一切正常，真机上报 `level0 is corrupted`** | **MonoBehaviour 文件名与类名不一致** | 改名使二者完全相同 |
| iPad 上点击/拖动无反应，Console 有 `The referenced script on this Behaviour is missing!` | 同上 | 同上 |
| `Stopping profiler ... not able to send data fast enough` | 无线连接带宽不够 | 用数据线；不影响 app 运行 |

## 2.1 ⚠️ 最重要的一条：文件名必须等于类名

**Unity 要求 MonoBehaviour 的文件名与类名完全一致。**

本轮踩坑经过：脚本文件名为 `TapMoveCamera_V2.cs`，类名为 `TapMoveCamera`。

- **编辑器里能正常运行**（Unity 有回退机制，找不到同名类就用文件里第一个 MonoBehaviour）
- **打包后真机崩溃**，报 `level0 is corrupted! [Position out of bounds!]`
- 报错完全不提脚本，指向的是场景数据文件

**两种修法：**

| 做法 | 代价 |
|---|---|
| 改文件名（`TapMoveCamera_V2.cs` → `TapMoveCamera.cs`） | 无。在 **Unity 里**改名会同步 `.meta`，组件引用和 Inspector 参数都保住 |
| 改类名（`TapMoveCamera` → `TapMoveCamera_V2`） | 无——**只要是同一个文件**。场景里的引用按文件 GUID 存，改类名不影响 |

**⚠️ 但下次做 V3 时代价会出现**：V3 是新文件、新 GUID，Unity 认不出它与 V2 的关系，必须移除旧组件、挂上新组件、**重新填一遍所有 Inspector 参数**。而那些正是需要在设备上反复调的值。

**建议的长期做法**：Assets 里的文件名保持稳定（如 `TapMoveCamera.cs`），版本历史留在 Assets 之外的归档文件夹，并在代码里加版本号常量、显示在调试框里——这样在 iPad 上看一眼就知道跑的是哪一版，比文件名有用。

> **推论（值得单独记住）：编辑器里跑通 ≠ 真机上跑得通。**凡是改过脚本文件名或类名，必须在真机上验证一次。

# 第三部分：性能优化实录

## 3.1 两类问题必须分清

| | 症状 | 诊断工具 | 解法方向 |
|---|---|---|---|
| **内存问题** | 启动闪退、被系统杀死 | Unity Memory Profiler | 贴图分辨率、mipmap |
| **GPU 问题** | 能跑但帧率低 | 帧率读数、Unity Profiler | 渲染管线设置 |

**本项目两个问题都遇到了，且是先后出现的**：先解决内存（不然进不去），再解决帧率。

**设备约束**：iPad Pro 11" 一代（2018, iPad8,1, A12X, 4 GB RAM, iPadOS 26.4.2）。
iPadOS 给单个 app 的内存上限约 **2867 MB**，超过直接 SIGKILL。

## 3.2 诊断工具分工

### 一般诊断工具

| 工具 | 在哪儿 | 回答什么 | 何时用 |
|---|---|---|---|
| Unity Console | Unity 按 Play | 配置错误 | 每次改完场景 |
| Xcode Console | Xcode 运行时下方 | app 的运行日志（**其实是 Unity 打印的，Xcode 只是转发**） | 崩溃、异常 |
| Unity Profiler | `Window → Analysis → Profiler` | CPU/GPU 谁慢 | 掉帧定位 |
| Unity **Memory Profiler** | 需单独安装 | 内存被谁占（可到单个资产） | 内存超标 |
| Xcode Debug Navigator | Xcode 左侧 | 实时内存/CPU 曲线 | 每次真机运行 |
| 调试框内的帧率读数 | app 内 | 帧率、DPI | 耐久测试 |

**Memory Profiler 安装**：`Window → Package Management → Package Manager` → `+` → `Add package by name...` → `com.unity.memoryprofiler`

**⚠️ 抓真机快照的前提**：
1. Build 时勾 **Development Build** + **Autoconnect Profiler**
2. app 在设备上跑起来
3. Memory Profiler 工具栏的下拉从 `Editor` 切成设备（如 `localhost - nature`）
4. 再点 Capture

下拉留在 `Editor` 时抓的是编辑器自己的内存，与设备完全不可比。

**⚠️ Development Build 会额外占内存、拖慢性能、加剧发热。**
> **诊断用 Development Build，验收和正式实验必须用正常 Build。**

### GPU 优化诊断工具

**1. Unity Profiler —— 先分清是 CPU 还是 GPU**

Window → Analysis → Profiler（⌘7）

打开后左边选 Rendering 和 GPU 两栏。要看的是两条线谁更高：

GPU 高 → 画面太重（像素填充、阴影、透明叠层）
CPU 高 → draw call 太多（比如那个树实例化问题）

这一步必须先做，因为两者的解法完全不同。之前 RenderTexture 276 MB 那个线索指向 GPU，但那是间接推断，Profiler 是直接测量。

⚠️ 要测真机必须勾 Development Build + Autoconnect Profiler，在编辑器里测出来的数字对 iPad 没有参考价值——Mac 的 GPU 比 A12X 强太多。

**2. Frame Debugger —— 看这一帧到底画了些什么**

Window → Analysis → Frame Debugger

**这个是最直观的。**点 Enable 之后，它把这一帧的每一次绘制调用列成一个列表，你可以一步步往下点，左边的画面会一笔一笔地画出来。

它回答的问题是别的工具答不了的：

总共画了多少次？（列表长度就是 draw call 数）
哪一批占了最多次？（比如：植被画了 800 次，那就是实例化没生效）
有没有画了但看不见的东西？（画完又被挡住 = 纯浪费）
阴影、后处理各占几次？

你那个"Adaptive Probe Volume 上挂了 Camera"的怀疑，用它一眼就能确认——如果场景被渲染两遍，列表里会出现两组几乎一样的绘制序列。

它只能在编辑器里用（Play 模式下），但 draw call 的结构是跨平台一致的，所以看"画了什么、画了几次"完全有效。

**3. Rendering Debugger —— 看渲染管线的中间产物**

Window → Analysis → Rendering Debugger

URP 专用。可以把画面切换成各种中间缓冲：只看深度、只看法线、只看阴影贴图、只看透明层叠加了多少次（overdraw）。

最有用的是 Overdraw 视图——森林场景里树叶层层叠叠，同一个像素可能被画十几遍，这是移动端 GPU 最典型的杀手。开这个视图，越亮的地方就是叠得越厚的地方。

**4. 建议的用法**

如果哪天要继续挖帧率，顺序是：

Profiler 定性：GPU 还是 CPU
GPU 的话 → Rendering Debugger 看 Overdraw，找植被叠层最厚的区域
CPU 的话 → Frame Debugger 数 draw call，找哪批物体没批合并

30 fpt 时上述检测可暂时不测，这几个工具留着，等有明确需求（二十分钟耐久不达标、或换设备后要重新分配预算）再拿出来。

## 3.3 内存优化（3.03 GB → 0.76 GB，降幅 ~75%）

**Quality Settings（Mobile 等级）：**

| 项 | 值 |
|---|---|
| Global Mipmap Limit | **2 - Quarter Resolution** |
| Mipmap Streaming | 开启 |
| Add All Cameras | 开启 |
| Memory Budget | 256 |
| Max Level Reduction | 2 |

**其他：** 开启 Texture Mipmap Stripping（不把 iOS 用不到的最高 mip 层打进包）。

**效果：**

| 时点 | Total Resident |
|---|---|
| 优化前（被系统杀死） | ~3.03 GB |
| Quality Settings 优化后 | 1.28 GB |
| 后续渲染优化后 | **0.76 ~ 0.93 GB** |

**结论：内存问题已彻底解决，余量充足（上限 2.87 GB）。**

### 关于逐张纹理优化

曾建议按"近景/远景/重要性"逐张设置 iOS Max Size。**在自由行走的场景里这个分类需要考虑被试的行动路径。**

**可行的做法**：预先规划哪些场景可能产生与被试较多的互动，分析场景中更容易引起被试注意力的植物，给植被 Alpha Base Map 建立单独的 Mipmap Limit Group，只让重要植被使用更高一级纹理精度，而全局继续保持较低纹理质量。这样能在效果和性能之间找到一个适合的平衡点。

**但在做之前先用 Memory Profiler 看 Tree Map 排前十**，只优化真正占地方的那两三个资产包。本项目因内存已达标，此项未执行。

## 3.4 GPU 优化（9 fps → 稳定 30 fps）

**这一节是本文档最有价值的部分：每一项都记录了帧率收益与画质代价。**

### 生效的改动

以下为一次性配置，具体哪个收益更大没有测量，表中的收益仅为估计

| 改动 | 位置 | 帧率收益 | 画质代价 | 最终采用 |
|---|---|---|---|---|
| Resolution Scaling → **Fixed DPI 150** | Player Settings | 大 | 轻微变软（iPad 尺寸下不明显） | ✅ |
| **Shadow Max Distance → 40** | URP Asset | 大 | 远处无阴影 | ✅ |
| **Shadow Cascade Count → 2** | URP Asset | 中 | 几乎无 | ✅ |
| 关 **Film Grain** | Global Volume | 小 | 无（噪点本就不该有） | ✅ |
| 关 **Bloom** | Global Volume | 中 | 高光柔和感消失 | ✅ |
| 关 **Motion Blur** | Global Volume | 中 | 无。**且运动模糊是已知晕动诱因，关掉是双重收益** | ✅ |
| 关 **Adaptive Probe Volume 物体上的 Camera 组件** | 场景 Hierarchy | **待验证，疑似很大** | 无 | ✅ |
| **SSAO → Blur Quality Low / Samples Low** | Mobile_Renderer | 中 | 轻微 | ✅ |
｜**Tree Distance** | Terrain Settings | - | - | ✅ | 

### 试过但回退的改动

| 改动 | 为什么回退 |
|---|---|
| **关闭 SSAO** | 画面"像漂白了一样"，明暗接缝的层次消失 |
| **Rendering Path: Forward+ → Forward** | 阴影层次变少、画面变平，**空间层次感明显减弱** |
| **关闭 Tonemapping (ACES)** | 画面严重漂白。ACES 是完整的色彩映射曲线，**即使未开 HDR 也在实际压缩高光、加深暗部**。Unity 那条警告说的是"效果不完全准确"，不是"不起作用" |
| 关闭 Opaque Texture | 未采用。本项目水面折射可能依赖它（注：它与树叶的 Alpha 通道**无关**，alpha cutout 不需要它） |
| 关闭 Depth Texture | 不可关。水、雾、SSAO 均依赖 |
| 关闭 WaterCausticsEffect | 未采用。该插件仅在河流的 Boundary Box 内生效，且焦散用纹理模拟，开销有限 |
| Render Scale 0.8 | 未采用。已叠加 Quarter mipmap + DPI 150 两层降采样，再降画质代价过大 |

### ⚠️ 一条必须关闭的功能

**`Use adaptive performance`（URP Asset 底部）建议关闭。**

它会在设备发热时自动降画质——对普通应用是好事，**对实验是有害的**：意味着不同被试、不同室温下看到的画面质量不一样，引入不可控的混淆。**宁可帧率掉，也要保证所有人看到的是同一个东西。**

### 内存构成的变化（可用于判断优化是否作用在渲染管线上）

| 类别 | 优化前 | 优化后 |
|---|---|---|
| RenderTexture | 276.1 MB | **94.6 MB** |
| Texture2D | 207.2 MB | 207.2 MB |
| Mesh | 205.8 MB | 205.8 MB |
| Shader | 75.2 MB | 75.0 MB |

RenderTexture 大幅下降说明改动确实作用在渲染管线（阴影贴图、后处理缓冲）上。Texture2D / Mesh 未变，因为没有动资产。


## 3.5 最终状态

| 指标 | 数值 |
|---|---|
| 帧率 | **稳定 30 fps**（全程几乎无波动） |
| 冷机启动时 | 45~50 fps |
| 内存 Total Resident | 0.93 GB / 上限 2.87 GB |
| 热状态 | **`Serious`** |
| 手感温度 | 温，不烫手 |

**关于"稳定 30"**：上一轮是 25↔50 剧烈跳变，这一轮死死钉在 30。**稳定比高更重要**——帧率抖动比稳定低帧率更让人不适，也更影响手感参数的可测性。

## 3.6 ⚠️ 画质代价的研究学含义（这一条不是技术问题）

本项目中，**环境的视觉丰富度就是自变量的实质内容**。软性魅力（soft fascination）依赖于环境本身足够耐看。

因此优化的取舍标准与普通应用不同：

- **"糊"（分辨率下降）损失较小** —— 还是同一个环境
- **"平"（光影层次丢失）损失更大** —— 变成了另一个刺激

SSAO 与 Forward+ 之所以被回退，正是这个理由。**这是研究判断，不是技术判断，只能由研究者在真机上做。**

# 第四部分：诊断流程与验收标准

## 4.1 标准测试路线（必须固定下来）

优化前后的数字要可比，就必须走同一条路。

**本项目的标准路线**：从山谷出发 → 走到西侧小路 → 返回起点，约 5 分钟，途中须经过植被最密处与视野最开阔处。

**这条路线有两个用途：**
1. 每次优化前后走一遍，帧率才可比
2. **交给学生做验收**：改完场景走一遍，帧率不达标就打回

## 4.2 四条诊断流程

### 流程一：内存

1. Development Build + Autoconnect Profiler
2. 走到场景最"重"处
3. Memory Profiler → 切到设备 → Capture
4. 看 **Tree Map**，按大小排序，只看前十

**验收线**：正常 Build 下峰值 **< 2 GB**（不要卡在 2.87）

### 流程二：二十分钟耐久 ⭐

**这是最要紧、也最容易被跳过的一项。** 干预时长是 20 分钟，而设备会发热降频。

1. **正常 Build**（不是 Development）
2. **让 iPad 彻底凉透再开始**——起点必须干净
3. 拔掉线、常温房间——插着线充电会更热，结果不可比
4. 正常走动 20 分钟，**每 5 分钟记一次帧率**
5. 同时在 Xcode Console 的 Filter 框输入 `thermalState`，记录状态变化的时间点

**要看的是曲线形状，不是绝对值：**
- 平的（30/30/30/30）→ 过关
- 下滑的（45/40/32/26）→ **危险**。被试在干预前后半段接受的不是同一个刺激，且掉不掉还取决于室温——这是无法在论文里辩护的混淆

### 流程三：帧率定位（仅在流程二不达标时）

Development Build + Profiler 连真机，看 CPU 与 GPU 哪条线更高：
- **GPU 高** → 画面太重（贴图、透明植被叠层、阴影）
- **CPU 高** → draw call 太多（如下方的树实例化问题）

两者解法完全不同，必须先分清。

### 流程四：包体大小

`ls -lh` 看 `.app`，或 iPad 设置 → 通用 → iPad 储存空间。优先级最低，装得下即可。

## 4.3 热状态监测

iOS 不开放具体温度读数，但开放**热状态**。Xcode Console 里 Filter `thermalState`：

| 状态 | 含义 |
|---|---|
| `Nominal` | 正常 |
| `Fair` | 温 |
| `Serious` | **系统已开始降频** |
| `Critical` | 严重降频 |

**比手摸客观，且带时间戳。**

# 第五部分：给场景制作者的规范

**这一节比任何单次优化都重要。**优化不应是"做完场景再清理一遍"，而应是**从现在起场景内容的建设约束**。否则会需要优化第二遍、第三遍。

## 5.1 纹理导入规格

| 项 | 要求 |
|---|---|
| 格式 | **ASTC**（iOS 专用压缩）。不设可能在用未压缩格式，差数倍内存 |
| Max Size | 普通颜色纹理 1024；法线 1024；Mask/AO/Height 512~1024；树叶与透明植物 1024 |
| Generate Mip Maps | 开启 |
| Stream Mip Maps | 开启 |
| **Read/Write** | **关闭**（开启会让内存翻倍） |

**批量操作方法**：Project 窗口里按文件夹全选 → Inspector 支持多选编辑 → 一次设置。

## 5.2 材质与模型

- 树木材质须支持 GPU Instancing（否则每棵一次 draw call）
- Terrain Tree 须使用 `Nature/Soft Occlusion` 着色器
- 树木、灌木必须有 LOD
- 减少不同材质与不同 4K 纹理的**种类数**
- 清除 URP 材质中实际不用的 Height / Mask / Displacement 纹理引用

## 5.3 Terrain 设置

| 项 | 建议 | 注意 |
|---|---|---|
| Tree Distance | 5000 → **800** | 活动区域仅约 100 m，渲染 5 km 内的树是纯浪费；此项几乎不影响观感 |
| Detail Distance | 120 → 30~60 | **会影响观感**，需边看边调 |
| Detail Density | 1 → 0.3~0.6 | **会让草变稀**，放最后调 |

**⚠️ 这几个值改的不只是性能，是被试看到的画面。必须在 iPad 上边看边调，不要照抄数字。**

## 5.4 验收标准

不是"尽量优化"，而是明确的三条：

1. 正常 Build 下峰值内存 **< 2 GB**
2. 活动区域内 **稳定 30 fps 以上**，且无剧烈抖动
3. **20 分钟不出现持续下滑**

达标即停。

## 5.5 明确否决的方案

**分区异步加载 / Additive Scene / Addressables 分块加载 —— 不做。**

两个理由：

1. **尺度不匹配**：活动区域是一公顷且被遮挡物封死，为一公顷做跨公里尺度的流式加载没有意义
2. **对研究有害**：中途加载会产生卡顿，而**卡顿是强制夺取注意的事件**——它把被试从环境里拽出来、看向系统，与本项目要证明的机制（不费力的注意维持）正好相反

**一次性加载完、20 分钟内什么都不发生，才是本项目要的。**

同理，**启动页/加载画面也不需要**：每次测试都是先把场景设置好、让每个被试从同样位置同样朝向开始。

# 第六部分：未决问题

## 6.1 ⚠️ 热降频：30 fps 是降频后的地板

**最新观测**：稳定 30 fps 的同时，`thermalState` 为 **`Serious`**。

**这意味着 30 不是"没在降频"，而是"降完之后稳在这里"。**冷机时测到的 45~50 才是未降频能力。

**对研究设计的含义：**
- 被试拿到手的**一直是降频状态**（除非是当天第一个）
- 因此 30 反而是**可复现**的那个数，比 45 更适合当基准
- 但也意味着**这台机器的余量已经用尽**

**待验证**：正式做 20 分钟耐久测试时，须确认降频后是否还会继续下滑。若继续下滑，则必须换设备。

**Unity 下 Window → Analysis → Project Auditor**： 会一次性扫描整个工程，列出所有配置问题：没设 ASTC 的贴图、Read/Write 忘了关的资产、材质引用了用不到的贴图、着色器问题等等。输出可以直接变成给学生的整改清单。

## 6.2 设备决策

**问题不是"性能够不够"，而是"要不要花钱把画质买回来"。**

现状：稳定 30 fps 的代价是明显的画质损失（Global Mipmap Quarter + DPI 150），且画面质量与显示器上"差一个档次"。而画质损失伤的是自变量本身。

**参考信息**：11 英寸 iPad Air（M4）在电商平台叠加国补后约 3900~4900 元，教育优惠可用。M 系列 GPU 约为 A12X 的 3~4 倍，8 GB 内存。

**⚠️ 两条硬约束（若决定换设备）：**

1. **必须在正式收数据之前换。**屏幕尺寸决定画面占据的视野角度，而视野角度是晕动的主要变量。跑了几个被试再换，前面的数据作废
2. **建议仍买 11 英寸**，保持视野角度可比，也保住已在 11 寸上调定的手感参数

**⚠️ 零成本的先行验证**：免费 Apple ID 的描述文件支持最多 10 台设备。**借一台新 iPad 装一次**，把 SSAO、Forward+、Mipmap、DPI 全部调回高质量，走一遍标准路线看帧率。十分钟，直接回答"值不值这笔钱"。**在拿到这个数之前买是在赌。**

## 6.3 待做但本轮未做

- **20 分钟耐久测试**（正常 Build、拔线、常温、iPad 凉透后开始）
- **拖动语义设计**（本轮原定任务，被工程问题挤占）
- 调试框字号：`Debug Font Size` 从 22 改小到 10~12（V2 会按 DPI 自动放大，10 足够）
- 调试框中部分汉字在 iOS 上显示为方框（默认字体缺字），不影响判读，暂不处理
- 屏幕边缘手势：Player Settings 里有 `Defer system gestures on edges`。iPad 底边上滑会拉出 Dock，可能与拖动手势冲突。**待拖动真正在 iPad 上跑起来后再验证是否需要开启**

# 第七部分：内存占用统计

## 7.1 正式场景内存统计（统计日期：2026-10-17）

**背景**：旧 iPad Pro（2018，A12X，4GB 内存）进入正式场景（Virtual Nature）即被系统以内存超限终止（JetsamEvent）。性能面板显示该机留给 App 的可用内存约 3GB。同一 App 在 Mac 上运行（Designed for iPad）时占用约 4.38GB。

**统计方法**：在编辑器中读取正式场景实际会打包的全部资源（剔除标记为 EditorOnly 的物体），按 iOS 平台导入设置（压缩格式、最大尺寸、Mobile 画质档的全局贴图精度 = 降一级）估算每项装入内存后的大小。只统计资源，不含运行时开销（渲染缓冲、shader、物理碰撞体、Unity 自身等）。明细表：Unity 工程根目录 `MemoryReport_VirtualNature_iOS.csv`。

| 类别 | 清理前 | 清理后 |
|---|---|---|
| 普通贴图 | 918 MB | 690 MB |
| 贴图数组（地形材质等） | 838 MB | 约 200 MB |
| 网格 | 360 MB | 约 250 MB |
| 声音 | 70 MB | 47 MB |
| 地形数据 | 18 MB | 18 MB |
| **合计（资源部分）** | **约 2.2 GB** | **约 1.2 GB** |

## 7.2 本次清理（2026-10-17，画面无可见变化）

| 项目 | 节省 | 做法 |
|---|---|---|
| GTS 地形材质残留数据 | 683 MB | 移除主地形、南侧地形上的 GTSTerrain 组件。两块地形实际使用 MicroSplat 与 URP 地形材质，GTS 未参与渲染，却引用了两组未压缩的 8 层 2048 贴图数组 |
| 未压缩植物贴图（25 张） | 约 170 MB | iOS 平台改为 ASTC 6×6 |
| 旧道路网格（79 万顶点） | 114 MB | `ground_design/Road` 下的网格，物体本已关闭，改标 EditorOnly，打包时剔除 |
| Enviro 夜空贴图（3 张） | 约 55 MB | iOS 平台最大尺寸降到 512（场景为白天，看不到） |
| Enviro 自带音效（6 段） | 约 30 MB | iOS 平台加载方式改为压缩加载（CompressedInMemory） |

验证：清理前后在出生点四个方向各截一张图，前后差异小于同一时刻连拍两张的差异（差异来自风动与云的动画）。原场景与导入设置已备份。

同日另修一处 LOD 错误：地被植物 Ground_cover21（场景中 1579 株）的高精度模型不受 LOD 管控，任何距离都在绘制（详见迭代记录 C 第 2.6 条）。

## 7.3 尚可压缩但有代价的项目（未动）

- MicroSplat 地形贴图数组 4096 → 2048：可省约 114 MB，近处地面会变糊。
- 可读写网格 606 个、约 141 MB：部分为触摸功能必需（透明度表、结构烘焙），需逐个甄别。

## 7.4 结论与后续

- 旧 iPad 实测（2026-10-17，清理后的版本）：菜单界面 App 占用约 330 MB、系统剩余约 2.68 GB；点"实验条件"后约 5 秒、进度约 30% 时，App 占用由约 1.48 GB 在几秒内升至约 2.49 GB，随即被系统终止（EXC_RESOURCE / JetsamEvent，崩溃线程在上传贴图 mip 到 GPU）。结论：峰值出现在**场景加载阶段**（贴图读入内存与上传 GPU 同时进行），而非运行阶段；该机无法运行正式场景，不再继续适配。
- 新设备测试时应重点记录**加载过程中的内存峰值**，而不只是进入场景后的稳定值。
- 新设备要求：M 系列芯片、内存 8GB 以上、11 英寸。新设备到手后实测内存峰值，作为本表的对照。
- 场景改动后若新增大量资源，用同样方法重新统计，在本节追加一张带日期的表。

# 附录 C：清缓存的正确顺序

按代价从低到高，**一步一步试，不要一次全做**：

1. **删掉 iPad 上的 app** → Xcode 直接 ▶︎ 重装
2. 删 `~/Library/Developer/Xcode/DerivedData`（Xcode 缓存，会自动重建）
3. **关掉 Unity** → 删 Unity 工程的 `Library/Bee` 与 `Library/BurstCache` → 重开 Unity → Build 到**全新文件夹**
   - 此后第一次构建会很慢，**慢才是对的**，说明真在从头编译
   - 换输出文件夹**不足以**跳过缓存，因为缓存在 `Library` 里
4. 若仍不行，则不是构建流程问题 → 在编辑器里按 Play 判断：
   - 编辑器正常 → 问题在打包环节（首先怀疑**文件名/类名不匹配**）
   - 编辑器也异常 → 场景本身有损伤，考虑回退版本
