# 设计-开发交互方案 J

**【停下来】的通道分离：从世界参照的光圈，到三条独立通道的并行比较**
记录日期：2026-09-05
最后编辑：2026-10-28（补记第十一节：触摸规则修订）

---

## 研究问题与本方案的位置（上游已定，不在开发会话中重议）

机制是**不费力的注意维持**（软迷恋），不是临场感提升。交互的职能是补上屏幕自然相对真实自然的迷恋强度差额。

**本轮只做一件事：把【停下来】从点击通道里分离出来，并把三套方案同时保留在工程里以供上手比较。**不新增功能、不动其他交互。

本轮与方案 G 的关系是**接续与部分推翻**。方案 G 通过拆参数（`stopBandRadius` 从 `walkKeepDistance` 分出）修好了光圈的可预期性，并把由此产生的位移跳变判为「可接受的代价」。本轮的实测表明那个判断低估了代价——见第五节。

**本轮不作选型定论。**三个模式的优缺点记录在案，最终采用哪一套留待多轮自测与学生试用之后再定。

## 一、复盘：【停下来】走到本轮之前的全部历程

### 1.1 它在系统里的身份

理解后面一切问题的前提：**【停下来】没有自己的代码。**

`ResolveTapCore` 只算一件事——转向 + 位移多少。可走地面保持一个距离，不可通行对象保持另一个距离，落点已在保持距离之内 → 位移为零、只转身。所谓「停下来」就是这最后一个分支，是「距离已经足够近所以走 0 米」的几何副产品（方案D 第一节）。

方案F 5.3 据此否决了按四类意图分表记录日志：写入时做分类判断是「解释」而不是「事实」，而【停下来】这个类别在实现里根本不存在。

它的性质也与另外三类不同。《设计测试笔记-Psi》定性：【停下来】更接近**工具性操作**，不是自然动机。方案H 第五节把这条正式确定：原先讨论过的「默认值反转」（默认停下、走路才需要动作）决**不反转**，且**方案A 律 1「任何一次回到弥散都不能需要专门动作」就其对停下来的适用而言作废**——那是没有可运行系统时下的判断，反转要动导航核心架构，而实测中工具性停靠不构成负担。

### 1.2 三条宗旨（按分量排）

**（一）它是 Kano 意义上的必备属性，不能用频率衡量。**方案C 5.6：做了不会有人夸，不做整个交互不成立。当时驳回了「低频所以挂起」，判定那是范畴错误——用律 4（不为低频付全局代价）去衡量必备属性，等于把安全带放上性能属性的秤。

**（二）停不下来会直接污染因变量。**「不听使唤」「连滚带爬」这类感受落在**主观控制感与轻微挫败**上，而两签名检验押的正是**放松那一维**——挫败感恰好指向放松维度的反方向。方案C 5.7 因此留了一条：试用必须专门问「在坡上有没有觉得使不上劲」。

**（三）病灶在于「注意力不在操作上」，不在于「不知道规则」。**方案C 5.2 记的那句自述是整条线索的锚点：

> 我是设计者都容易出错，因为当时的注意力是放在环境上的。

由此推出：**事前练习解决不了这个问题**——练熟的是操作，而问题恰恰发生在不去想操作的时候。而「注意力放在环境上」正是实验要的状态。所以任何「让被试记住一条规则」的解法，在最需要它的那一刻最不可靠。

### 1.3 问题史（五个阶段）

**阶段一 · 借住在拖动里（V1–V2）。**拖动第一帧即取消移动，于是「想停」和「想瞥一眼」共用同一个动作，系统一律读成想停。V2 代码里那条「不要加『拖动幅度小就不停』这类启发式」的告诫，是这段借住关系留下的疤。

**阶段二 · 被赶出来（方案C，V3）。**边走边看剥离了拖动的停止副作用，缺口暴露。关键判断是：**这个缺口不是边走边看造成的**，停一直没有自己的家，边走边看只是让这件事变得可见。回退拿回的不是一个好的停，是那个重载——两边都要付，没有免费选项。

实测报告：想停 → 点身前地面 → 人还走一两米 → 以为没点中 → 再点 → 又设了一个新的短程目标 → **越想停越停不下来**（「传送带」）。

**阶段三 · 三次尝试与两条封死的路（方案C 5.3–5.5）。**

- 加大 `walkKeepDistance` 到 4.0：平地成立（连点变成幂等操作，传送带在机制上不成立），但**坡地推翻**——上坡时所有可见地面都在停止范围内、根本动不了；下坡时没有一击够得着、停不了。
- 由此得到那一轮最重要的否定结论：**一个参数不可能同时服务两个方向相反的需求**（「停」要它大，坡地导航要它小）。
- 阈值随地形自适应：被**参照系被偷换**的反驳杀掉——等价于画面底部一个按钮，而按钮更简单也更诚实。
- 并留下一条更强的结论：**任何单靠距离阈值、同时解决上坡移动与下坡停止的方案，必然是屏幕参照的**，所以「停」若要做好，必须走独立手势通道。

结论：维持 4.0，标为**已知限制**，且明确「是排期靠后，不是降级为可选」。

**阶段四 · 光圈（方案D 候选 → 方案E 实现）。**从调试用的可及范围圆环得到的思路：在脚下画一圈很淡的光圈。

方案D 的评估是「方向成立，但只是解的一半」：过了参照系那一关（世界参照、以人为中心、半径固定）、正对 5.2 的病灶（不需要记忆），但**它会说谎**（死区有两个半径，画在 4.2 上的圈对 2.7–4.2 之间的植物是假的）、**它解不了坡地几何**，因此与独立手势通道是可叠加而非替代关系。

方案E 第十一节实现完成。三个设计判断：判定本身已是世界参照（用水平距离，与它出现在画面哪儿无关）；**半径不是新参数**（由 `walkKeepDistance + arriveThreshold` 定死，两个数说了算早晚分叉，分叉的表现最坏——点在圈里却没停下来）；形态用 URP Decal Projector，因为它投出来的就是「水平距离 < R」这个集合本身，一致性由构造保证。

以及那次工具形态的纠正：**半径不该暴露，粗细浓淡恰恰只有眼睛能判、必须暴露**；参数挂 prefab、`ExecuteAlways`、Scene 里调 Play 里验。

**阶段五 · 拆参数（Psi 笔记 → 方案G，V5.6）。**实测暴露：光圈有时占满视野极易误触，有时在视野外根本停不下来，斜坡尤甚；同时「点得远走得近」。

方案G 4.1 判定这是**同一个病根的两面**——`walkKeepDistance` 一个数管两件方向相反的事，为满足「停」取 4.0，代价是每一次点地面的移动都被砍掉 4 米。

4.3 撤回了「统一停止带」——统一到 4.2 会把【我想看】和【我想摸】一起废掉。正确范围是：**停止带只对「点可走地面」生效**，因为「停」本来就是「点脚前面那块地」；崖壁与植被的早退不是「停」，是「你已经够近了」。

拆分结果：`stopBandRadius = 4.2`、`walkKeepDistance = 1.0`、光圈常驻。取值依据是几何不是手感：`stopBandRadius ≥ 眼高 ÷ tan(垂直FOV/2)`（51.28° → 3.54 m），达到此值点画面下缘才真正进入纯停分支，**连点才是幂等的**。研究者实测反馈：「这回感觉控制起来更有把握了。」

方案G 4.7 同时记下代价：边界上出现一个 **3.2 米的跳变**（4.19 m → 走 0；4.21 m → 走 3.2 m），无法调参消除；判为可接受，因为**这个跳变发生在一条画得出来的线上**。由此光圈从「可选的可见化」升格为**承重件**。

### 1.4 走到本轮之前的未决项

1. 坡上停不住，病根未定位。方案F 5.11 用旁观者系统排除了「滑行距离过长」（残余速度中位 0.153 m/s，最长 0.11 秒、最远滑出 3 厘米，是正常减速末端）。
2. 方案C 5.4 那个上下坡的几何冲突原封未动。光圈解的是可见性，不是几何。
3. 备选方案「停改为俯角判定」（方案G 4.8）挂着，留待斜坡问题复发时启用。
4. 方案C 5.8 的独立手势通道选型未定（长按已排除；双指点击 vs 快速连点未决）。
   > **2026-10-05 补注**：「长按已排除」只在边走边看下成立。走看分离下回正漂移在代码层停用，排除长按的那个冲突不存在，长按已改作后退的触发手势，见第十节。

## 二、本轮的困惑：为什么还要改

方案G 之后光圈是可预期了，但多轮自测暴露出**两个方向相反的失效**，而它们的根源是同一个：**光圈是世界参照的，它在屏幕上的大小与位置不是常数。**

同样半径的光圈，随视点朝上朝下、随站位高低、随坡度，在屏幕上的覆盖从「充满半个屏幕」到「完全看不见」之间变化。而 `Radius` 在 Game 模式下极为敏感，稍微调大调小，屏幕上的范围就明显改变，非常难以控制。

**失效一 · 光圈不可见时。**想停下来，还需要先向下摇一次相机，把光圈内的范围找回视野。这与光圈设计的初衷完全背道而驰——它本来就是为了消除「抱着『可能是点这里』的心态去试探」而做的。

**失效二 · 光圈可见时。**它会和其他交互动机冲突。想去一个离自己很近的目标点，而那个点恰好在光圈之内，**人根本动不了**。

一句话概括：**因为融入到世界环境中，它的可控性明显降低；看不见的时候「停」变得极为复杂，看得见的时候它又吞掉别的动机。**

于是本轮的问题被提为：**是不是真的需要为【停下来】提供一条独立通道了。**

## 三、选项的重新划分

讨论开始时把选项分成「世界参照 vs 屏幕参照」，这个划分不成立。研究者重新给出了正确的定义：

> **独立通道 = 【停下来】遵循一套独立的「输入—处理—反馈」流程。**

按这个定义，真正的轴是**手势 vs 接口**，参照系退回它该在的位置——只用来解释光圈为什么不稳定，不再是选型判据。

三个候选：

| | 停的判据 | 有没有「指定区域」 | 有没有新手势 |
|---|---|---|---|
| **A 光圈** | 落点与自身的**水平距离** < 4.2 | 有，世界里的一个圆盘 | 无 |
| **B 俯角带**（方案G 4.8） | 落点相对相机的**俯角** > 阈值 | 有，屏幕下缘一条固定的带 | 无 |
| **C 独立通道** | 按钮位置 或 手势本身 | 按钮有位置，手势无 | 按钮无，手势有 |

### 3.1 俯角带（方案G 4.8）被否决——正式作废

研究者的判断：**它两头的缺点都占了。**它仍然占用点击通道（所以还是会和「我想走到那儿」抢），却又已经和世界脱钩（所以也不再有「我指着那块地」的自然性）。既然都要在屏幕上切一块地方出来，那么一个明确的按钮比一条不画出来的带诚实得多。

**补充的技术依据**：方案G 内部对这条方案自相矛盾。4.8 说俯角判定「不需要光圈」，4.7 说「将来即便把停改成俯角判定，那条边界仍须以某种方式画出来，只是形状从地上的圈变成画面下缘的一条」。而屏幕下缘画一条线，就是当初发明光圈要绕开的那个 HUD。

**结论：方案G 4.8 的俯角判定备选，本轮正式作废，不再作为未决项保留。**

### 3.2 一处教条翻转，须落文

方案C 5.5 以**原则**否决屏幕参照（「违背我们的交互理念」）；方案G 附录判据 2 写的是「**屏幕参照优于世界参照**」。这是一次有理由的修订（有了可运行系统和实测之后），但此前未被显式记为「推翻旧结论」。**本轮正式记入：方案C 5.5 的原则性否决作废，判据以方案G 附录判据 2 为准。**

### 3.3 决定用实验而非推演

研究者的判断：三种通道在体验上的差别，靠推理推不出来，必须亲自感受。因此**三套方案全部实现并同时保留在工程里**，用一个下拉框切换，另外两套自动失效。

## 四、修改方案

### 4.1 核心认识：停 = 中断，不是目标设定

研究者定的语义：

> 停下来点击后，不论在任何情况下，马上停止。没有 Walk Distance，也没有 Arrive Threshold，马上停。用户主动的停下来权重高于所有其他的停下来。但当用户不主动干预时，系统内部机制照旧——走到目标点停下来、聚焦某物时保持距离停下来，这些都不变。

这个定义把一件事理顺了：**距离概念从头到尾就不该出现在「停」里面。**`walkKeepDistance` 和 `arriveThreshold` 是「一次移动在哪里结束」的参数，与「用户喊停」无关。

**由此推翻本轮讨论中一度出现的说法「停止带塌回 1.2」。**正确表述是：**B、C 模式下不存在停止带这回事。**「点可走地面」这个分支回到和其他所有层一样的处理——`keepDistance + arriveThreshold`，那不是「停」，是「你已经够近了，不必再走」。这恰好就是方案G 4.3 自己写的那句话：停止带只对可走地面生效，*因为「停」本来就是「点脚前面那块地」*。把「停」搬走之后，这个特例自然消失。

### 4.2 中断只中断移动

研究者定：**只针对移动时候的停下来，不影响其他行为，包括旋转。**身体在旋转过程中点停下来是没反应的，该怎么旋转还怎么旋转，因为旋转并不难以控制。

加上一条既有约束，最终范围是：

| | 停止时 |
|---|---|
| 移动指令 | **取消** |
| 余速 | **保留**（不清零） |
| 身体旋转 | **不动** |
| 指示手 | **不动**（方案D 1.2：手永远走完收回动作） |

**余速为什么不清零**：律 3，停下的余速是身体存在感的一部分。而且算出来的数支持这个决定——`moveSpeed = 1.2`、`deceleration = 3.5`，全速中断的滑行是

```
距离 = 1.2² / (2 × 3.5) = 0.206 m
时间 = 1.2 / 3.5 = 0.343 s
```

这个 0.21 m 正是方案C 5.3 记下并判为「主观评价自然」的那个数。**所以不需要为「停」新增任何刹车参数。**

**由此结清一笔悬了两个月的账。**方案C 5.2 的实测抱怨是「想停，点了身前地面，人没有立刻停——还得走一两米」。现在两头都有数：自然到站的滑行是 3 厘米（方案F 5.11 实测），全速中断的滑行是 21 厘米（上式）。**那「一两米」从来不是减速造成的，是那一击又设了一个新目标造成的。**「停不下来」自始至终是语义问题，不是物理问题。

### 4.3 实现（V5.9 → V5.10）

**改动清单**

| 文件 | 内容 |
|---|---|
| `TapMoveCamera_V5.cs` | 10 处补丁：`StopMode` 枚举、`StopNow()`、`StopBandRadius()` 分岔、按钮拦截、双击判定、光圈按模式启停、调试框两行 |
| `TapLog.cs` | 新增两列：停止模式、停止触发 |
| `StopButton/StopButton.cs` | 新建。IMGUI 绘制的常显圆形按钮 |
| `Editor/TapMoveCamera_V5Editor.cs` | 新建。按模式隐藏不相干参数 |

**`StopNow(trigger)` 是唯一的停止实现，三条通道共用。**四行：`isMoving = false`、目标点收回脚下、清空 `lastRequestedDistance` / `lastGrantedDistance`。这条是「工具不许是第二套实现」的直接应用——若按钮自己写一遍停止，将来改了减速逻辑，三个条件会静默地不一致，而实验结果照样出得来。

**`StopBandRadius()` 按模式分岔**：非光圈模式直接返回 `walkKeepDistance + arriveThreshold`，`stopBandRadius` 字段**真的不参与计算**，并在 Inspector 上隐藏。※ 藏一个仍在生效的参数是最坏的做法；隐藏必须以真的失效为前提。

**双击写在 V5 的输入层里，不做成独立组件。**理由：双击判定必须发生在消费这次点击的那个输入处理里；独立组件就得自己再读一遍 Touchscreen，那是第二套输入实现。

**双击用「事后取消」而非「延迟执行」**：第一击立刻照常跑完（转向 + 出发），第二击到了才把它撤掉。若为了等第二击把所有单击都压后，整套点击导航会一起变钝——那时测到的是延迟，不是双击。

**双击必须同时带屏幕距离窗**（`doubleTapRadiusMM = 8`）。V2 那条告诫说的就是这个：连续快速改道点击会误触发。改道的两击落在画面不同位置，慌乱补点的两击落在几乎同一处，靠距离窗把两者分开。有了它，时间窗可以放宽（0.35 s）而误触发反而更少。

**按钮必须在按下那一帧被拦截。**V5 直接读 Input、不走 EventSystem，所以手指按在按钮上时相机脚本同样会看到一次点击，射线穿下去打到脚前的地面。不拦的话，按一下停止按钮，人会一边停下来一边又走出去两米。命中判定用的矩形与画出来的是同一个（同源）。

**按钮按下即停，不等松手。**常规 UI 在松手时触发是为了留一条「滑开取消」的退路。这里不需要——停是幂等的，而「我按了它没马上停」恰恰是本项目要消除的那种感觉。

### 4.4 三条实现路上的错误（本轮的错误记录）

**错误一 · 用 `Font.CreateDynamicFontFromOSFont` 做中文兜底。**Unity 内置字体不含中文，为让按钮上能写「停下来」，写了一条「取不到字体就用系统字体 PingFang SC」的兜底。这个 API 在编辑器的 IMGUI 里字形图集会反复重建，表现为：字不出来、串成图集里别处的文字（实测显示为编辑器自己的「Gizmos」）、改字号就跳位。

**修正**：删掉这条兜底，改为 `Label Mode` 两选一——`Text`（需自备中文字体）或 `Glyph`（实心方块，媒体播放器上通用的停止符号，零字体依赖）。选 Text 但无字体时自动退回 Glyph 并出一次警告，**绝不留一个空圆**。

**教训**：兜底路径若比主路径更不可靠，它就不是兜底，是一个更隐蔽的失败点。宁可明确退化到一个稳定的次优形态。

**错误二 · 用「距屏幕中心的毫米偏移」定位按钮。**编辑器 Game 视图和 iPad 的宽度不同，同一个偏移值在两边落到不同位置——一边贴边一边悬空。

**修正**：改为锚点 + 距边缘的毫米距离（`H Anchor` / `Side Margin MM`）。**凡是要跨设备成立的位置量，必须从会变的那条边量起，不能从中心量。**

**错误三 · 一度把「停止带塌回 1.2」当作 B、C 的形态描述。**这是把中断误当成了目标设定。研究者纠正后才理顺（见 4.1）。**教训**：当一个新语义被引入时，先确认它属于哪一类操作，再去描述它的参数——反过来做会把旧类别的词汇带进来。

### 4.5 关于测试方法的一次否决

讨论中曾提出用行为数据评估三套的顺畅度，具体是「走同样路线，点击次数越少越顺畅」「每次点击行走距离越大越好」。这个方案被否决，理由分两层：

**技术层面**：一次「停」在三套里花的点击数是设计常数（Ring 1 击、Button 1 击、DoubleTap 2 击）。双击天生每停一次多花一击，跑同一条路线停同样多次，它的总点击数**必然**最高——那个排序在按下第一次 Play 之前就已经确定。更麻烦的是，「点击少」可能恰恰是坏消息：如果停一次太贵，很多本来想停的时刻就放弃了，表现为点击少、每击距离大，而按该指标它是最优。

**根本层面**（研究者的判断）：

> 用行为来评估用户执行的是否顺畅，就像根据钢琴师手指的动作来评估他弹的乐曲优不优美一样不靠谱。

**结论：本轮及后续的通道比较以主观感受为唯一判据。**日志不关，但**不作结果变量，只作索引**——某个瞬间觉得不对劲时，靠 30 Hz 位姿记录和第三人称回放把那一段找回来看。

**须记明的一条保留**：行为数据确实说不出「顺畅」，但有一件事只有它能看见——**想停但算了**。那种时刻不会留在感受里，因为根本没做那个动作，事后也想不起来。若三套主观感受接近，值得回头翻一眼停止频率。

## 五、比测试结果更重要的一个发现

**删掉停止带解锁了一整类此前不存在的行为，而这与选哪条停止通道无关。**

研究者的实测报告：

> 我第一次能够走到场景中很多特定的地方，比如站在一块石头上，或精确的站在水边。
> 这是我第一次能够在我设计的小径上走完一个完整的循环。而之前在光圈模式下做不到这种掌控性，总是走着走着就不知道走到哪去了。

这两件事在 B 和 C 里都成立，因为 4.2 米的死盘在两者中都不存在。**它不是按钮或双击的功劳，是删掉 `stopBandRadius` 的结果。**

**这件事在方案A 3.2 里被预测过**：观察需求（退开一点、绕到侧面、站上去看）应当由**平移**承担而非旋转；「我在控制环境」那种感觉的来源是纯旋转过多。4.2 米的死盘挡住的恰好就是这一整类平移。所以「走着走着就不知道走到哪去了」不是导航不准，是**观察需求被迫全部由转头来满足**。

**由此修订方案G 4.7 的判断。**当时把 3.2 米跳变记为「可接受的代价」。现在看，停止带的代价远不止一个跳变——它切掉了一整类短距离定位行为，而那类行为是方案A 认定的核心观察手段。**方案G 4.7 的代价评估低估了实际损失，本轮修订。**

## 六、三个模式的实测体会（研究者自测，不作选型定论）

### 6.1 A · 光圈

**优点**

- 视野里有一个清晰的光圈时，**点击停止是最自然的**。判定可见，不需要记任何规则。
- 界面上没有额外的停止图标，不干扰沉浸感。
- 学习代价最低。
- **它不是一个被操作的对象**——「停」就是「停在这儿」，意图与执行之间没有插入工具。
  这是三个模式里独有的性质，也是「自然」二字的真正来源。详见 **6.5**。

**缺点**

- **光圈显示不在视野内时**，想停要先向下摇相机——与设计初衷背道而驰。
- **光圈显示出来时**，实现不了「往前挪几步」——近处目标落在圈内，人动不了。
- 半径在 Game 模式下极为敏感，微调即引起屏幕覆盖的明显变化，难以控制。
- 掌控性不足：**走着走着就不知道走到哪去了**，无法在设计好的小径上完成一个完整循环。

### 6.2 B · 按钮

**优点**

- 界面中有一个**稳定的锚点**，任何时候想停都可以点它。工具功能被独立出来后，整个流程的可控程度更高。
- 解放了「往前挪几步」（与 C 共有）。
- 心理层面的价值：**知道如果控制不了，点它就可以。**

**缺点与两次修正**

**问题一 · 指南针效应（位置在底部中央时）。**

> UI 和世界是两层，而按钮始终保持在底部中间的位置，它无形中给人一种指南针的暗示。当切换目标点、点击了侧边某处、摄像机转身掉头时，那个按钮保持在底部中间，总有一种「我开始偏离了方向」的感觉。

**诊断**：病因是**位置，不是图层**。画面底部正中在第一人称视角里有特定语义——那是「我正前方」。任何常驻在那个坐标的东西都会被读成航向标记，世界绕着它转时读出来就是「我偏了」。角落没有这个语义。

**修正**：挪到右下角（`H Anchor = Right`）。选右侧的理由是多数人右利手，且从右下角伸拇指遮挡的是右下一小块，从正中伸进去手掌会压住画面下半部分中间——那正是脚前地面所在。

**实测结果**：**显著消除指南针效应，沉浸感明显提高。**

**问题二 · 距离代价（费茨定律）。**

挪到角落之后，想停时手要移动一段不短的距离才能触到按钮。这与 Fitts's Law 一致：`T = a + b·log₂(2D/W)`，距离 `D` 增大则获取时间增加。

※ 须记明一个常被误用的经验：桌面 UI 里「屏幕角落最容易点」靠的是鼠标指针被屏幕边缘卡住，等效目标宽度无限大。**触屏没有这个性质**，手指不会被边缘挡住，所以那条桌面经验在 iPad 上不成立。

**研究者对这个代价的解读**（本轮最有意思的一段观察）：

> 这个按钮操作起来不是那么方便，这让我越来越不想去点这个按钮。这产生的影响在于，这个工具性的操作对在虚拟自然中的互动干扰会越来越小，更多的时候，我会依赖点击场景中某个目标，让它自然停下来。相比较【双击停下来】的那种便宜的方法，操作困难的按钮反而沉浸感会有所提高。

进一步的判断：

> 如果操作很方便，我可能会更频繁的使用它，这就会导致对工具性的依赖越来越高。即使自然停靠这条路被打通了，但双击操作太简单了，可能反而覆盖了自然停靠的效果。

**这条推论指向一个尚未确立的原则：工具性操作的成本不该被最小化，它应当高到足以让自然路径保持首选。**本轮不将其定为原则，理由见 6.4 的存疑。

### 6.3 C · 双击

**优点**

- **沉浸感最高**：画面上没有按钮，世界里没有光圈，什么提示都没有。
- 解放了「往前挪几步」（与 B 共有）。
- 停止随时可用，与任何其他交互都不冲突。

**缺点**

**问题一 · 动机层次的错位。**

> 双击操作是一种停下来的工具，而点击是我走过去，后者是我在世界中的一个动机，前者是我控制工具的一个动机。这种感觉很微妙，但总是感觉有点出戏。

**问题二 · 时序区分需要过一下脑子。**

> 在连续点击几个目标之后，想通过双击停下来，这种单击和双击的切换是需要过一下脑子的，这就造成了一些操作上的失误。比如本来是想去某个地方，结果下意识的手一抖，点了双击，结果停下来了。然后当我意识到我需要单击的时候，我已经从世界的沉浸感中脱离出来。

**这条实测比方案C 5.2 原来的说法更锋利。**5.2 说病灶是「注意力不在操作上时想不起规则」；实测到的不是想不起来，而是**两种动机挤在同一条通道上、只靠时序区分，于是每次都要花一拍去做那个区分**。

而按钮没有这个问题——它的工具动机有自己的**位置**。区分是空间性的（手指放哪儿），不是时序性的（点得多快）。**空间区分不要钱，时序区分每次都收费。**

**问题三 · 方案C 5.8 给快速连点的论证被推翻。**

5.8 当时的理由是：「想停、发现没停、本能地再点一下，而那一下恰好就是停止手势」，把本能当成优势。实测到的是同一机制的另一面：「本来是想去某个地方，结果下意识的手一抖，点了双击，结果停下来了。」

**同一个本能，在想停时帮你，在不想停时害你，而系统无法分辨——它们在输入层是同一个事件。**这不是调 `doubleTapWindow` 或 `doubleTapRadiusMM` 能解决的：窗收紧则难触发，放宽则更易误触发，两头在同一条轴上。**这是结构性的，不是参数性的。**

**结论：方案C 5.8 中「快速连点因不需要记忆而占优」这一论证，本轮由实测推翻。**

### 6.4 一处必须留在案上的存疑

6.2 中「工具变贵反而好」这个解读，有一个竞争解释未被排除：

**读法一（研究者的）**：按钮是安全带。日常停靠由「点个目标自然停下」承担，工具很少用到，其价值是心理层面的。工具贵一点反而好，因为它把自己从常规流程里挤了出去。

**读法二**：按钮太贵，于是行为被改变以绕开它。不再「停在我想停的地方」，而是「停在附近有个可点目标的地方」——目的地被工具的成本悄悄改写，而这种妥协恰好是感受报告不出来的那一类（见 4.5 的保留条款）。

**分辨它们的问题**：那些没按按钮的时刻，最后是不是停在了想停的地方？

**后续自测时须专门留意此项。**若「想停但没按」的时刻很少且都停到位 → 读法一成立，「工具应当有成本」可升格为原则；若这类时刻不少 → 读法二，则当前位置过头，应往中间挪或加大直径（`W` 也在费茨公式里，与 `D` 可分开调）。

### 6.5 光圈为什么"最自然"：一条在它被换掉之后才看清的优点

三个模式里，研究者对光圈的评价是「视野里有一个清晰的光圈时，点击停止是最自然的」。这一节记录那个"自然"到底是什么，因为**它在光圈被换掉之后才被解释清楚，而解释出来的东西比光圈本身更长命。**

#### 触发这次理解的一个误判

一次实测中，研究者在走向远处目标的途中产生了「想停下来」的念头，而手上做出的动作是**点击近处的地面**——那设定了一个新目标，不是停止。随后误以为系统「停不下来」（日志核查证明系统一切正常，见 6.6）。

研究者的复盘：

> 在真实自然环境中，人们只要有我想停下来的念头，身体马上停下来。而我当时在第二次点击的时候，脑子里就是这个念头，但实际上给系统的信号是，我要走到另外一个目标点。

**关键在于手伸向了哪里。**意图是「停」，动作是「指脚前那块地」——**那恰好就是光圈的语义。**在具身直觉里，「停」往往等于「停在这儿」，而不是「按一个停止键」，所以指向脚前的地面是一个非常自然的表达。这个误判因此是一份反向证据：它说明光圈的语义与身体直觉是对齐的。

#### 为什么对齐：梅洛-庞蒂的手杖

研究者的判断：

> 它最接近真实世界中的具身体验，有点像梅洛-庞蒂帽子拐杖的那些比喻，它们和我的身体行为是统一和一致的。而独立通道则把它们给拆开了。

那个比喻的要害不是"用得熟"，而是**盲人的手杖不再是一个被感知的对象，它并入了身体图式**——感知的边界从手掌移到了杖尖。判据是：**它有没有从「对象」变成「器官」。**

光圈始终待在被感知者那一侧：判定发生在世界里、以身体为中心，「停」就是「停在这儿」，意图与执行之间**没有插入一个需要被操作的东西**。所以它不需要被瞄准，也不需要被记住。

这同时解释了方案D 当初为什么判定它「过了参照系那一关」，以及方案E 11.1 为什么坚持"看得见的别扭好过看不见的别扭"——那些都是这条性质的局部表现，只是当时没有被统一命名。

#### 两层区分：哪些是媒介逼的，哪些是我们自己选的

「工具与具身分家」这件事，讨论中一度被整体归为媒介固有成本。研究者修正了这个说法：**它不单纯是媒介问题，也和设计意图有关系。**准确的表述分两层——

**第一层 · 媒介固有，躲不掉。**真实自然中「停」不是一个动作，是「不继续」——没有信号，意图本身就是执行。屏幕自然必然要插入一个信号。任何屏幕方案都逃不出这一层，区别只在那个信号有多贵。

**第二层 · 设计选择，可逆。**我们**进一步**选择让那个信号**保持为对象**（按钮或双击），而不是让它并入身体图式（光圈）。理由是稳定性：并入身体图式的东西会随身体状态变形——光圈随俯仰、站位高低、坡度变形，正是这条性质的代价；而外在于身体的工具不变形。

**这一层是我们自己下的判断，将来可以重新审视；第一层不行。**记录时必须把两层分开，否则将来会把一个可逆的设计选择误当成媒介的铁律。

#### 与研究机制的关系

机制是**不费力的注意维持**。而「把意图翻译成一个要被瞄准的信号」这一步消耗的正是**定向注意**——与因变量在同一条轴上。所以工具通道的成本不是可用性问题，是**直接顶在机制上的**。

由此还得到一条对练习目标的限制：**如果工具是被设计成保持为对象的，练习的目标就不该是"让它并入身体"**——那个方向与设计意图相反，而且大概率做不到，因为它每次都要被瞄准。练习该达到的是更弱的东西：**想停时不必犹豫用哪个动作。**（※ 这与方案C 5.2「事前练习解决不了这个问题」不冲突：5.2 反对的是用练习弥补「记不住规则」，而这里要的是把「想停 → 发出信号」这个映射从审慎变为程序性。**5.2 的适用范围应收窄为：练习不能替代可见性，但可以建立自动性。**）

#### 结论

**光圈的这个优点是真的，而且是三个模式里独有的——它不是"看得见所以好学"，是"它不是一个对象"。**

**但它的副作用目前仍无解**：世界参照导致它在屏幕上的大小与位置不是常数，由此产生的两个方向相反的失效（见第二节）没有找到更好的解决方案。本轮换用独立通道是在这个前提下的取舍，**不是因为光圈的设计思路错了。**

这条须记明，否则将来回看会误以为光圈整体被否定。它没有。**被否定的是它的实现，不是它的语义。**如果将来出现一种既保持"停 = 停在这儿"的具身语义、又不随身体状态变形的表达方式，这条路应当重新打开。

### 6.6 一条关于误判的观察：判断可以先于事实成立

6.5 那次误判还带出一件独立的事，值得单独记。

研究者当时的结论是「怎么没停下来？」，而事后的日志核查证明**系统一切正常**：三份日志约 200 次点击，重定向全部成功，一次「走过头」都没有；所有「没走到」的记录都能由"在到达之前又点了一下"解释；筛选"间隔足够走完却没走到位"的击，结果为空。

**误判的成因是视觉证据在最后一段消失了，而这是几何决定的、且是设计有意为之。**

```
地面点掉出画面下缘的距离 = 眼高 / tan(垂直FOV / 2) = 1.7 / tan(25.64°) = 3.54 m
停靠位置 = walkKeepDistance = 1.00 m
→ 走向地面目标时，最后 2.54 m 是"盲走"：目标已在画面外，看不到自己在接近它
```

这 2.5 米在 1.2 m/s 下要走两秒多。**代码层面查实：点裸地面属于浏览层 → 不设视线锚 → `UpdateFocusPitch` 直接 return → 相机不会低头去盯着地面目标。**这是方案G「聚焦 vs 浏览」分工的既定结果，理由正当（每点一次地面画面都往下压一下，逛起来会非常烦，那是用例 3 当初要避免的）。**所以这是一笔已知的交换，不是缺陷。**

真正值得记的是研究者的这句自述：

> 这个念头来的太快，让我轻易的判断「怎么没停下来？」

**误判先于事实成立了。**而如果当时顺手又点一下，那一击会设一个新目标，然后「它停不下来」这个结论会被进一步坐实——**这正是方案C 5.2 那条传送带的另一个成因：不是机制失效，是判断早于事实。**

**对正式试用的直接后果**：被试报告「停不下来」时**不能直接采信**，必须先查日志确认那一击到底走完没有。研究者本人是设计者、清楚系统怎么工作，仍然在这上面判断错了一次。

## 八、相机参数的一次澄清（顺带记录，非本轮主线）

讨论中问及「第一人称视角应当用什么相机参数」，结论记录如下，因为它与停止带的取值直接耦合：

**FOV**：iPad Pro 11" 显示区约 247×178 mm，横持 40 cm 处，屏幕实际张角约水平 34°。当前设置是水平 69°、垂直 51.28°，比几何正确值宽约一倍——但这几乎是所有第一人称应用的做法，因为几何正确的 34° 会使转身变成高频动作，而纯旋转过多正是方案A 3.2 诊断的问题来源。**结论：51.28° 垂直是合适值，不动。**

**且现在不能动。**FOV 与停止带死死绑在一起：`画面里最近的地面 = 眼高 / tan(垂直FOV/2)`，51.28° → 3.54 m，40° → 4.67 m，60° → 2.94 m。`stopBandRadius = 4.2` 成立的前提是 3.54 < 4.2。收窄 FOV 会让光圈模式立刻退回「非纯停」，A 组对照即废。

**Gate Fit 建议由 Horizontal 改为 Vertical。**开了 Physical Camera 之后真正说了算的是 Gate Fit；选 Horizontal 意味着水平角锁死、**垂直角随屏幕比例浮动**，而所有近场/停止带推导用的都是垂直 FOV。改成 Vertical 后垂直角在任何比例下都是 51.28°，代码里的数与文档里的推导才对得上。（代码本身用 `ScreenPointToRay` 取实际投影矩阵，不会算错，只是文档推导会与实机对不上。）

**景深：建议关闭。**三条理由——(1) 当前 f/16.87 + 25 mm 的超焦距约 1.26 m，对焦 10 m 时 0.63 m 到无穷远全清晰，实际没有景深；(2) URP 里 Aperture / ISO / Shutter Speed 只在有 Depth of Field 的 Volume Override 且模式为 Physical Camera 时才起作用，否则是装饰；(3) **最要紧的一条**：相机景深是「只有一个平面清晰」，而人眼是看哪儿哪儿清晰——被试的眼睛可以自由扫视屏幕，被虚化处不会因注视而变清晰，这会被读成「这是一段影像」而不是「这是一个地方」。且软性魅力靠的正是细节丰富但不索取注意的视觉信息，模糊掉的正是这部分。附带：DoF 是纯 GPU 开销，而 A12X 的瓶颈是热节流。

**眼高 1.7 m 合适，同样属于「现在别动」**——它也进了停止带公式。

## 九、待解决 / 未决

1. **三个模式的选型未定。**须经多轮自测 + 学生试用之后再定。**本轮不下结论是有意的。**
2. **6.4 的存疑未排除**：「工具变贵反而好」vs「行为被成本改写」。后续自测须专门留意「想停但没按按钮」的时刻及其结果。
3. **持握姿势未固定。**按钮的距离代价取决于 iPad 怎么拿（双手横持 / 单手托 / 架桌面），费茨定律里的 `D` 由持握姿势决定。当前手感只对研究者此刻的姿势成立。**正式跑被试时持握方式必须固定并写进流程**，否则这个参数在不同被试身上是不同的值。
4. **坡上停不住的病根仍未定位**（方案F 待解决项 9）。方案C 5.4 的几何分析（下坡最近可点地面 8 m 以上，没有一击够得着）与方案F 的观察从未接上过。旁观者系统现在能记录每次点击的落点水平距离与当时坡度，**这是一个可以先做掉的核对**。※ 若最终选定 B 或 C，此问题自动消失，因为停不再依赖距离。
5. **中文字体未加。**当前按钮用 Glyph（实心方块）。若最终要显示「停下来」三字，需导入含中文的字体，且 Import Settings 中 `Character` 选 `Custom set`、`Custom Chars` 填「停下来」——中文字体本体十几 MB，Dynamic 模式会整个打进 iPad 包。
6. **旁观者回放看不到主动停止。**按钮和双击的停止写进了 CSV，但未接入旁观者的判定快照（那要动 `TapSerial` 那条接缝，风险大于收益）。回放里能看到人停下来，但分不出是哪条通道触发，CSV 里能分。
7. **光圈的副作用仍无解。**世界参照导致它在屏幕上的大小与位置不是常数，两个方向相反的失效（第二节）没有找到更好的解决方案。**本轮换用独立通道是取舍，不是判定光圈的语义错了**（见 6.5）。若将来出现一种既保持「停 = 停在这儿」的具身语义、又不随身体状态变形的表达，这条路应当重新打开。

8. **练习方案未定。**独立通道把工具与具身分开是**有意为之**，因此被试需要预先练习。练习目标应设为「想停时不必犹豫用哪个动作」，**不应**设为「让工具并入身体图式」——后者与设计意图相反，且大概率做不到。练习的排程、两组对称性等属实验设计常规，不在本文档展开。

9. **`stopBandRadius` 的代码默认值仍是 4.2、`walkKeepDistance` 的代码默认值仍是 4.0**，调好的值只存在于 prefab 实例上。这是方案C 9.3「参数换岗位」那类风险的残留。未处理。

## 十、补记：我想去 · 后退（2026-10-05，V6.1）

本节是一次小改动的补记，不单独成篇。它放在本方案里，是因为它修订了 1.4 第 4 条「长按已排除」，而且它与【停下来】一样，是挂在点击通道旁边的一条独立手势通道。

### 10.1 起因

测试中发现，被试想观察某株植物时几乎只有一次机会。第一次没点中植物，射线落到植物后面的地面上，人就直接走到了植物后边。要把它重新带回视野，只能拖动屏幕转身，而大幅拖动会让人丢失方向感（交互测试综合分析报告A 第 26 节把这一点归因于旋转时缺少身体参照）。经过多轮自测，研究者决定以增加一个手势为代价，加入后退：走过了想看的东西，退几步，让它回到视野。

### 10.2 为什么长按现在可以用

方案C 5.8 排除长按的理由是：「手指按在屏幕上」已经分配给了「暂停回正、保持视角」，两者冲突。这个冲突只存在于边走边看（WalkAndLook）。在走看分离（StopOnLook）下，回正漂移在代码层停用，冲突的一方不存在。当前场景使用的正是走看分离，所以后退只在走看分离下工作；切到边走边看时，整个后退分组在面板上隐藏，脚本侧也真的不参与计算。将来如果改回边走边看，长按的冲突会重新出现，这一条需要重新评估。

### 10.3 学习代价为什么可以接受

1.2 第三条说，【停下来】的病灶是「注意力不在操作上」，规则在最需要它的时刻最靠不住。后退的使用时刻不同。被试意识到「我走过头了，想再看一眼」时，注意已经从环境转回到自己的意图上，这是一个反思性的时刻，记起一条规则的可靠性高得多。此外，后退不用就没有成本，一句话就能教会，而且它替代的是代价更高的拖动转身。真正的代价是误触，即慢一点的点击被读成长按。对此的处理是把时长阈值暴露成参数，并在日志里记录每次点击的按压时长，用数据决定阈值放在哪里。

### 10.4 设计决定

后退是身体动作，不是时间回放。它保持当前朝向和俯仰，身体沿画面朝向的反方向平移；它不沿走过的轨迹倒回，也不恢复先前的视角。错过的东西因此会从画面两侧和下缘重新进入视野，不需要旋转。

长按只是一个触发信号，不是持续控制。按住达到时长阈值的那一刻即开始后退；退多远由参数决定，何时停与何时抬手无关，抬手也不算一次点击。研究者否决了「按住持续后退、松手即停」的方案，理由正是这一条。

后退与前进共用路径采样、到站判定和余速滑停，只换一组速度参数（速度、起步加速度、收尾减速度）。起步与收尾都有缓冲。

以下四条是实现时定下、经研究者自测认可的行为：长按触发后手指再滑过拖动阈值，按拖动处理，走看分离下即停；后退途中再次长按，从当前位置接着再退一段，速度不中断；后退途中点击，新的点击覆盖后退；行走中长按时，先按基本移动的减速度刹停，余速归零后再起步后退。最后一条可由「只在站定时响应」开关关闭，关闭后行走中的长按被忽略，抬手按普通点击处理。

### 10.5 被否决的方案：用压力代替长按

研究者曾考虑用按压力度代替长按来减少误触。此路不通，理由有两条。第一，iPad 从未支持手指的压力感应，只有 Apple Pencil 有压力数据；用手指接触面积近似压力，会随手指粗细和按压角度大幅变化，不可靠。第二，即使硬件支持，「用力按」本身也是一个需要分配注意去控制的动作，与方案A 律 3「存在感不需要被管理」相冲突。

### 10.6 实现与日志

脚本 `TapMoveCamera_V5.cs` 中新增 Inspector 分组【我想去 · 后退】，位于停止模式之后、我想看之前。参数为：`enableBackStep`、`longPressTime`（默认 0.5 s，参考 iOS 系统长按默认值）、`backStepDistance`（默认 1.5 m）、`backStepSpeed`（默认 0.6 m/s）、`backStepAcceleration`、`backStepDeceleration`、`backStepOnlyWhenStanding`（默认关）。

`TapLog` 末尾新增「按压秒」一列：点击行记录这一击从按下到抬手的时长，后退行记录触发时已按住的时长，其他行留空。意图列新增「后退」与「后退·受阻」两个值。会话备注中写入本轮的后退参数。

已知限制：旁观者回放能复现后退的过程（回放的是位姿），但时间轴上不标出后退事件，与第九节第 6 条的情况相同。

## 十一、补记：触摸规则修订（2026-10-28，真机测试后）

**起因**　10-27 第一次真机测试（被试熟悉旧版操作）。点中可触摸物却没摸到的情况里，最常见的是"远处点一下只走过去、到跟前要再点一下"：她有 9 次第一下没摸到，其中 3 次走到跟前就离开了。熟悉规则的人尚且如此，新被试看到的是"点了一株植物，人走过去，什么也没发生"，与"这株不能摸"无法区分。另有两类混淆：点中花（Flower）会锁住视线走过去、手却不伸；手收回前再点，系统只说"手正忙"。

**原理**　交互规则要让被试从一次操作的结果就能读懂世界：能摸的东西点一下就摸到，不能摸的东西点了等于没点。中间态和"要点两下"都要求被试先知道系统内部的规则。触摸是这个交互条件里最重要的时刻，它进行时不应被别的操作打断。

**决定**
1. 两态：场景里能点中的东西只有可触摸物和地面；普通植物点了等于点后面的地面。原先"锁住视线走过去、却不能摸"的中间态取消（聚焦保留为可关闭的选项，默认跟着可触摸走）。
2. 一击即摸：点中可触摸物，不论多远，走到跟前并伸手。原先"远处点植物可能只是想看"的顾虑，在两态下不再成立：能点中的植物只有可触摸的。
3. 走近可打断：手伸出来之前，新的点击或拖动（拖动即停）取消这次触摸。
4. 触摸中锁定：下蹲或伸手开始到手收回，不响应任何操作，位置和镜头不动。下蹲只在触摸时发生，算触摸的一部分。锁定期间的点击照记，以免被当成"点了没反应"。

**仍待真机验证**　一击即摸在远距离（走好几米后才伸手）时，动作与点击是否脱节；走近途中轻微调整视角会取消触摸，被试是否察觉。

## 附：本轮确立或修订的判据

1. **工具动机应当由空间区分承担，不应由时序区分承担。**空间区分不要钱（手指放哪儿），时序区分每次都收费（点得多快）。这是 B 相对 C 的结构性优势，也是本轮最长命的一条。

2. **画面底部正中在第一人称视角里有航向语义。**常驻在那个坐标的 UI 会被读成航向标记，世界绕着它转时读出来是「我偏了」。这不是 UI 图层的性质，是那个特定坐标的性质。角落无此语义。

3. **凡是要跨设备成立的位置量，必须从会变的那条边量起，不能从中心量。**（错误二的推论）

4. **兜底路径若比主路径更不可靠，它就不是兜底，是一个更隐蔽的失败点。**宁可明确退化到一个稳定的次优形态。（错误一的推论）

5. **隐藏一个参数，必须以它真的失效为前提。**藏一个仍在生效的参数是最坏的做法。

6. **同一个本能在两个方向上作用，而系统无法分辨时，那是结构问题，不是参数问题。**（推翻方案C 5.8 的依据）

7. **中断类操作不该用目标设定的词汇去描述。**先确认操作属于哪一类，再去描述它的参数。（错误三的推论）

8. **工具是「对象」还是「器官」，是一条独立于「好不好用」的判据。**并入身体图式的表达（光圈）不需要被瞄准也不需要被记住，但会随身体状态变形；保持为对象的工具（按钮、双击）不变形，但每次都要被瞄准。**这是一笔用具身性换可控性的交易，须自觉地做，不可默认。**（6.5）

9. **「工具与具身分家」要分两层记：媒介逼的那一层躲不掉，设计选的那一层可逆。**把后者误记成前者，会让一个可以重新审视的判断变成不可动摇的铁律。（6.5）

10. **被试报告的失效不能直接采信，须先与日志核对。**判断可以先于事实成立，而错误的判断会通过后续操作把自己坐实。（6.6）

11. **屏幕参照优于世界参照。**（沿用方案G 附录判据 2；本轮正式作废方案C 5.5 的原则性否决）

12. **工具不许是第二套实现。**（沿用；本轮体现为三条通道共用一个 `StopNow()`）

13. **概念推导到「规则该长什么样」即止。**（沿用方案G 附录判据 1；本轮体现为「靠推理推不出来，必须亲自感受」）
