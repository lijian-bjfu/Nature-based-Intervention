## 第一阶段 搭建基础框架
 
### Phase 1 Unity - iPad

该流程基本框架是：在 Unity 中生成 IOS 项目，Xcode 打开该项目进行编译，Xcode 工程不是一个需要长期维护的东西，它是每次生成出来的中间产物。在这个环节中， Xcode需要两个注册。第一是Bundle Identifier，它是对APP本身的ID标注。第二是Team ID，是开发者本身的身份验证。这两项内容需要记录在Xcode项目的Signing and Capability设置页下。Xcode将 Bundle ID和Team ID 提交 Apple 询问这两个ID是否可用。如果 Apple识别到 Team ID 是一个是一个免费账号，那它会根据该账号的权限，对于Bundle ID的运行开放一些相关的权限。比如Apple只能允许只能允许运行7天等等。

这两项签名都可以在Unity下来设定，以保证项目在不同的电脑端迁移，这些信息仍能够保留。Unity每次生成iOS项目的时候，如果发现有旧的版本，会提示，会询问是否 Replace 还是 Append。

为了便于操作，在第一次运行的时候，Unity端只设定Bundle ID，不设置Team ID。Team ID在Xcode里手动的进行选择，运行成功之后再把这个能够被认可的Team ID再贴到Unity里去，并把Unity里面自动签名的开关打开。这样以后运行的时候，就不需要每次都在Xcode里再设置一遍，而是直接打开Unity。生成的项目直接能跑。按照上述流程，建议Unity每次更新后在构建项目的时候，选择 Replace，Xcode关掉项目，再重新打开运行。

## 第三阶段 交互开发与测试

Create: 2026-06-28

### 总原则
数字自然干预系统（iPad）交互设计方案 V1

本项目旨在构建一个基于 iPad 的数字自然干预（Digital Nature Intervention）系统，通过沉浸式的自然环境体验和人与自然元素的交互，缓解个体焦虑、压力等负性心理状态。与传统游戏不同，本系统并不追求高操作自由度，也不以探索效率或游戏挑战为目标，而是关注一下几个方面：

* 自然环境的持续沉浸（Immersion）
* 低认知负荷（Low Cognitive Load）
* 低操作负荷（Low Interaction Load）
* 注意力持续停留于自然环境（Attention on Nature）

总之，本项目的交互设计原则并非来源于游戏设计，而是来源于数字健康干预与环境心理学，希望让交互逐渐”隐形”，使用户更多地关注自然环境本身，而非操作系统。

例如在导航方面：

不适合用于本项目的交互模式如在移动屏幕端广泛使用的虚拟摇杆：通过在屏幕左下角放置方向控制器，对空间导航进行控制精确。但由于可能导致用户注意力频繁离开自然环境、需要不断查看控制器，会有更高的学习成本和认识负荷。因此排除。

本项目采用的方案是：点击目标自动移动。用户点击自然环境中的目标位置，系统会自动地转向目标 - 前进行走- 到达附近停止。该设计的有点是符合人们现实世界的直觉性的行为模式：看见目标 → 走过去。在整个过程中，用户无需持续控制方向。对于提升环境沉浸感，聚焦自然环境本身有一定优势。

总体上，当前交互具有以下特点

* 操作方式简单，仅需点击与拖动；
* 导航与观察符合现实世界行为模式；
* 用户始终掌握交互主动权；
* 摄像机运动具有连续性，不存在明显机械感；
* 身体运动与头部观察相互独立，但能够自然衔接；
* 参数化设计，后续可通过实验调整移动速度、减速度、观察范围与转身速度。

### 交互设计原则

整个系统遵循以下四项设计原则。

**1. 单一手势完成多数操作**

避免引入复杂的多手势体系。例如：

* 双击
* 长按
* 双指缩放
* 双指旋转
* 虚拟摇杆
* 功能按钮

这些交互虽然能够提供更多功能，但会增加学习成本与认知切换，不符合数字干预的目标。因此，V1版本主要保留：

* 点击（Tap）
* 拖动（Drag）

两种最自然的触控方式。

**2. 导航与观察分**离

人在自然环境中的行为可分为两个层面：

第一层：移动身体（Navigation）

第二层：转动头部观察（Observation），系统分别对应两种交互：

- 移动，通过点击场景（目前是地面）某个位置，身体移动到目标位置
- 观察，通过拖动屏幕，原地转头观察环境

这种设计符合现实世界中的行为模式：看见 → 转头观察 → 决定是否走过去。

> 目前先不做一边移动身体，一边持续控制方向的设计，后续根据实际的体验效果再决定是否要加入。

**3. 交互主动权始终属于用户**

系统不会强制用户完成一个动作，而是考虑用户交互操作的底层意图。例如：当摄像机自动移动过程中，如果用户开始拖动屏幕，那么系统应立即认为，用户现在希望观察环境，而不是继续前进。因此系统会执行以下行为：

* 自动移动结束
* 摄像机减速停止
* 进入观察模式

用户无需额外点击”取消移动”。整个交互过程保持连续且符合用户当前意图。

**4. 操作不应打断自然体验**

交互设计的最终目标并非提高控制效率，而是降低系统存在感。用户应该始终感受到“我正在自然环境中行动”。而不是“我正在操作一个软件”。因此系统要替代用户负责更多底层交互逻辑处理和协调工作，而用户仅负责表达意图。


### 交互流程

目前V1流程如下：

进入场景 → 拖动屏幕观察 → 持续拖动观察 → 点击地面 → 摄像机缓慢转向 → 自动移动 → 用户继续观察 → 拖动屏幕 → 自动停止 → 继续观察 → 再次点击 → 继续移动

整个过程中不存在模式切换按钮。用户仅通过“点击”、“拖动”，即可完成全部导航。

### 当前技术方案

**1.点击导航**

- 采用 Raycast 获取点击位置。
- 系统记录 Target Position。
- 随后进入自动导航状态。


**2. 摄像机移动**

移动采用：速度驱动（Velocity Driven）而不是固定速度移动。系统包含三个参数：
- Move Speed
- Acceleration
- Deceleration

以此在实现不同运动中平滑的切换，例如，从开始移动 → 逐渐加速 → 结束移动 → 逐渐减速。


**3. 地形跟随**

场景中摄像机始终保持距离地面约1.7m的高度，模拟人的一般视角。实现方式为：摄像机向下发射Raycast，实时获取 Ground Height。以 Ground Height + Eye Height 保持摄像机高度。那么即使地形存在起伏，摄像机始终保持接近真实站立高度。

**4. 观察模式**

观察模式通过用户拖动屏幕模拟四处观看的效果
- 在观察时不移动身体，仅改变 Head Yaw、Head Pitch。同时设置左右观察极限、上下观察极限。接近极限时，旋转速度逐渐降低，一次模拟真实人体在转头存在生理限制。
- 当用户继续拖动屏幕时，理解为用户需要进行更多观察，以当前视角为基础，重复上面的有限制的视角环扫。

**5. 身体旋转**

身体旋转发生在点击新的移动目标后，如果该目标与当前目标产生角度偏差，身体会发生转向的过程。在转向速度上，设置一个可调节的参数 Body Turn Speed。在头部回正速度上，设置可调节参数 Head Return Speed。二者独立控制。

**6.移动与观察状态切换**

系统建立了两个主要状态：Navigation、Observation。在两个状态转换时，设定以下规则：在用户移动过程中，突然拖动屏幕。此时预估用户的当下目标是观察环境，那么系统立即退出 Navigation，进入Observation 状态，摄像机开始减速停止。整个过程无需用户额外操作。

### 已解决的关键交互问题

目前已经解决的问题包括：

- 移动过程中能够立即进入观察模式，无须等移动结束才能观察，从而增强用户主动控制感。
- 移动停止具有惯性。采用 Deceleration 避免立即停止的生硬感，符合人体运动体验。
- 点击移动与拖动观察互不干扰。修正了 Head Yaw 残留导致的反向摆动的问题。采用的方案为：当用户点击新的目标时，将当前实际朝向作为新的 Body Yaw。摄像机因此能够自然连续地转向新的目标。
- 头部观察存在角度限制。人在静止时四处观察，头部会天然受到生理限制。因此在旋转观察状态下，没有使用 360° 无限旋转，限定了旋转角度，更加符合真实人体观察行为。

### 后续计划

交互层面，下一阶段将重点完善人与自然元素之间的交互，而非继续增加导航复杂度。

计划包括：

1. 点击自然对象自动接近至交互距离；
2. 建立自然对象交互半径（Interaction Radius）；
3. 自然元素反馈（植物、水体、动物等）；
4. 基于不同自然对象设计差异化交互行为；
5. 完善整个数字自然干预体验流程。

后续设计仍将遵循”低负荷、高沉浸”的原则，使用户更多关注自然环境本身，而不是交互系统。

该部分交互在场景有了足够的完成度后再执行。
