## 研究问题与本方案的位置（上游已定，不在开发会话中重议）

机制是**不费力的注意维持**（软迷恋），不是临场感提升。交互的职能是补上屏幕自然相对真实自然的迷恋强度差额。

**本轮不设计新功能，也不开发新内容。**方案 A–F 铺完了「走过去 / 我想看 / 我想摸 / 世界的反馈 / 旁观者」这条主线，第一系统与第二系统均已跑通。本轮做的是对**已有基础交互的清算与打磨**——起点是研究者自己写的《设计测试笔记-Psi》，那份笔记把体验中积累的问题从理论层面重新框了一遍，归为**行动类**与**旋转类**两类，并明确了它们「只能靠被试主观报告测量、不能在开发阶段单方面保证」。

研究者对本轮的定位是明确的：**趁问题还少的时候清算，不把它们遗留到后续环节。**问题积累越多，解决起来越复杂。

**须记明的一条边界**：Psi 笔记把「看见但走不过去」归到 Plausibility Illusion 与 BIP 上，并把 BIP 操作化为被试可标记、可自陈的东西。这与方案 A/D 确立的立场——presence 只作**设计阶段的否决器**，不进研究框架、不作因变量——在措辞上贴得很近。本轮不改变该立场：**Psi 相关操作化停留在设计验收层，不进入正式实验的因变量清单。**这条界须在后续讨论中保持，否则容易滑过去。

## 一、本轮处理的五个问题（源自 Psi 笔记）

| Psi 笔记中的问题 | 类别 | 本轮结果 |
|---|---|---|
| 走过去·不可预期性（点得远、走得近） | 行动 | **解决**（拆参数） |
| 停下来的控制（光圈忽大忽小、不可预期） | 行动 | **解决**（拆参数 + 光圈常驻） |
| 点击即旋转（近处也转、转与走割裂） | 旋转 | **水平方向解决**（现有参数），垂直方向新欠一笔 |
| 聚焦目标 vs 环视浏览 | 旋转 | **取消问题**（改为查世界），落地为聚焦/浏览层判定 |
| 边走边看（脚步不为目光停留而慢下来） | 旋转 | **未动**，留待下一轮 |

**五个问题里，两个是被取消的，不是被解决的**——「停下来需要独立手势通道」与「系统须区分聚焦与浏览两种动机」。取消掉的问题不会在下一轮以别的形状回来，这比解决它们更有价值。

## 二、本轮最重要的方法论教训

**这一条排在功能之前，因为它的代价是本轮实际付出的最大一笔。**

前半程（约三分之一的讨论量）用于在概念层重新发明相机的自由度分配：视线锚、内聚、锚融入、锚衰减、锚脱落、视野区/余光区、俯仰跟随与不跟随……推演出一整套规则体系，绘制了两轮设计概念图。

**而其中的核心结论，在 `TapMoveCamera_V5` 里已经躺着现成的实现。**

| 概念层推导出的规则 | 代码里既有的东西 |
|---|---|
| 「视野区内点击不触发旋转，余光区触发」，屏幕参照、一次性判定、单参数 | `turnDeadZoneAngle`（默认 6°），语义完全一致，只是值太小 |
| 「转向与前进被切成两段，是结构缺陷，需新机制」 | `turnBeforeMoveAngle`（默认 60°），是一条**显式规则**，改一个数即可关闭 |
| 「点击不改变俯仰」 | 代码事实如此：`headPitch` 全脚本只由拖动与回正写入，点击从不触碰 |

**教训不是「少讨论概念、多试参数」。**正确的表述是：

> **概念讨论推进到「我知道这条规则该长什么样」就够了，接下来第一件事是去代码里找它，而不是去设计它。**

本项目的交互脚本是三千七百行、六个版本迭代出来的，其中沉着大量已经解决过的问题。**默认它没有，是错误的默认。**后续进入任何新议题，应先用一次工具调用把相关参数捞出来，再谈方案。

**另一笔纯粹的空转**：讨论中曾把「多点几下 = 聚焦」重新提出为解法。而方案B 第七节早已判定「反复点击同一目标是空转：手指持续遮挡画面、且未换来任何新信息」。**已作废的条目被重新捡回，正是方案文档反复警告的那件事，本轮亲自踩了一次。**这从反面证明了「作废条目必须显式记录」这条文档纪律的必要性。

### 2.1 概念讨论仍然留下的三样东西

浪费是真的，但不是全部。以下三样参数试不出来：

**一、判断力。**能一眼认出 `turnDeadZoneAngle` 就是那条边界、`stopBandRadius` 该按几何取值而非手感调——这来自先把概念想清楚。若只调参，25° 会被当成一个凑出来的手感值，而不是一条**有推导上限**的规则。

**二、两个被取消的问题**（见第一节）。取消一个问题只能在概念层完成。

**三、代价清单。**位移跳变、垂直光流、参数串岗、边缘斜移——四条全部写进了 `Interaction/README.md` 的用例表。它们不是调参调出来的，是推演出来的。**只调参会得到一组好用的值，但不知道它赔掉了什么**，直到某天被试报告一个怪现象。

## 三、旋转类问题一：点击即旋转

### 3.1 问题性质

Psi 笔记里这一条实为两件事：

1. **点近处也旋转**——点画面中心稍偏一点，画面就要挪一下。研究者的描述是「眼球是死的，像机器人」：现实中换注意不必换朝向，而系统里注视、头朝向、行进方向塌成了同一个量。
2. **转向与前进被切成两段**——先原地摇过去，摇完才起步。而**纯旋转产生光流却无视差**，读起来是「画面在动」而不是「我在动」，这正是方案B 诊断过的晕动来源。

### 3.2 修改思路

概念层推出的规则是：

> 点击的瞬间，看命中点落在画面的哪个区域。落在视野区内，不旋转；落在余光区，旋转到对准它。此后不再判定。

四条性质：**屏幕参照**（不随地形变形）、**形状固定**（可学）、**一次性判定**（不持续追踪，与方案B「判定无状态」同源）、**单参数**。

研究者对此的表述是分工的说法：「用户的角色，就是要判断余光区内是不是有他感兴趣的东西。」

### 3.3 解决方案：无需任何代码改动

`turnDeadZoneAngle` 的实现与上述规则一字不差。其判定过程为：先 `FoldHeadYawIntoBody`（把头部偏航折进身体朝向），再算命中方向与当前朝向的水平夹角——**折叠之后，这个夹角就是命中点在屏幕上离画面中心偏了多少度。**

**它有一个可推导的硬上限**：

```
水平半张角 = atan( tan(垂直FOV / 2) × 宽高比 )
```

垂直 FOV 51.28° 时：4:3 → 32.6°；iPad Pro 11"（1.43）→ 34.5°；16:9 → 40.5°。

**超过这个数，死区盖满整个屏幕，旋转永远不会发生**（因为点不到屏幕外面）。故可调范围是 0 到约 34°。

这条上限本身给出一个重要推论：**余光区必须是屏幕的外圈，视野区是屏幕的中心部分。**这与人的视野结构同构，不是巧合——屏幕在这里扮演的正是整个视野。

### 3.4 实测确定的参数组合

| 参数 | 旧值 | 新值 | 作用 |
|---|---|---|---|
| `Turn Dead Zone Angle` | 6 | **25** | 视野区半角。25° 落在 0–34° 的中间偏上 |
| `Turn Before Move Angle` | 60 | **180** | 关闭「先转后走」，转身整段融进行走 |
| `Turn Smooth Time` | 0.35 | **1.0** | 转向拖长，使转身过程明显落在行走里 |
| `Max Turn Speed` | 180 | **30** | 角速度上限，防止中段甩得过快 |

研究者实测结论：**「不论是远处的锚，还是眼前的锚，都和我期望的一致。」**

**一处须记明的机制辨析**：研究者最初观察到「调高 `Turn Smooth Time` 时锚融入自动产生」，并据此认为是转向速度参数解决了割裂。实际机制是——`turnBeforeMoveAngle` 才是造成割裂的那条显式规则；调慢转向只是让剩余角度拖得更长、更多地落在行走过程中，于是**绕过**了那条规则而非关闭它。**直接把 `turnBeforeMoveAngle` 设为 180 才是干净做法**，用转向速度去凑是治标。

### 3.5 代价

关闭「先转后走」之后，大角度目标会出现一小段斜向平移（脚本原注释警告过的「横着平移出去」）。但 25° 死区吃掉了中间那一大片，实际能触发大角度转向的只剩画面最外缘 25°–34° 那一圈，实测可接受。

**两个参数是配套的，不能单独调**：死区放大之后，能触发大角度转向的点击本来就少了。

**换屏幕比例或 FOV，死区上限跟着变，须重测。**这一条对 iPad 硬件决策有直接约束（11" 屏幅须保持，见既有记录）。

## 四、行动类问题：停下来，与「点得远走得近」

### 4.1 问题性质：两个现象，一个病根

Psi 笔记把它们记为两条：

- **停下来的控制**：光圈有时占据视野很大面积、极易误触；有时在视野之外、根本停不下来。斜坡处尤甚。
- **走过去的不可预期性**：点一个看起来很远的点，实际只移动了很短的距离。

**它们是同一个参数的两面。**V5.6 之前，`walkKeepDistance` 同时承担两个方向相反的职能：

| 职能 | 想要的方向 |
|---|---|
| (a) 走向地面时停在目标前多远 | **想小**：点哪儿走哪儿 |
| (b) 点多近算「停」（停止带半径） | **想大**：点画面下缘要能触发纯停 |

为满足 (b) 取 4.0，代价是 (a) 被牺牲：**每一次点地面的移动都被砍掉 4 米。**点 5 米走 1 米，点 4.5 米走 0.5 米。

斜坡上光圈变形则是同一个几何的另一面：4.2 m 是**世界半径**，上坡时那片地朝人抬起来、在屏幕上占满，下坡时掉出画面。**世界参照的量，被试用屏幕在操作。**

### 4.2 一处必须先澄清的混乱：「到达」有三个语义

研究者在 Psi 笔记中记录：到达目标有三种含义（走过去站上去 / 我想看看到了 / 我想摸摸到了），且它们在场景中交替出现。

代码层的对应是——`ResolveTapCore` 按射线打中哪一层取保持距离：

| 打中 | 保持距离 | 停止带上缘 |
|---|---|---|
| 可走地面（WalkTo） | `walkKeepDistance` 4.0 | 4.2 m |
| 崖壁 / 树干 / 大石（LookAt） | `viewingDistance` 2.5 | 2.7 m |
| 植被（Foliage） | `foliageKeepDistance` 0.5 | 0.9 m（触碰带） |

**光圈画的只有第一行。**于是站在原地、前方 3 米处：点一块地 → 停；点旁边一块石头 → 走到 2.5 m；点石缝里一丛蕨 → 走到 0.5 m。**三次点击在屏幕上差几个像素，结果完全不同。**

而这里还叠着已知的 C 类污染（透明通道与碰撞体未全场铺开）：**层判错，保持距离就跟着错**，表现为「这次停这么远、下次停那么近」。

### 4.3 一个被撤回的方案：统一停止带

讨论中曾提出「停止带对所有层统一，停变成一个数」。**该方案在实现前被推翻。**

理由：若停止带统一为 4.2 m，点 3 米外的一丛蕨会被判成「停」，人就永远走不过去摸它；点 3 米外的崖壁也不会再走近看。**统一的停止带会把「我想看」与「我想摸」一起废掉。**

**正确的范围是：停止带只对「点可走地面」生效**——因为「停」本来就是「点脚前面那块地」。崖壁与植被那两个早退分支不是「停」，是「你已经够近了，不必再走」（同时防止算出身后的落点导致后退）。这也与光圈画的一直是地面那一种相一致。

### 4.4 解决方案：拆参数（V5.6）

新增字段 `stopBandRadius`（Inspector 新栏「停下来」），默认 4.2 = 拆分前的旧行为，**只加字段不动别的，行为与拆分前完全一致**（一变量一次）。

```
判定：nearBandUpper = hitFoliage ? 触碰带上缘
                    : (intent == WalkTo) ? StopBandRadius()
                    : keepDistance + arriveThreshold
```

新增辅助方法：

```
public float StopBandRadius()
{
    return Mathf.Max(stopBandRadius, walkKeepDistance + arriveThreshold);
}
```

**取 max 是一条结构保证**：若 `stopBandRadius` 被调得小于 `walkKeepDistance`，落点会算到人的身后去，表现为莫名其妙地后退。用 max 之后这在结构上不可能发生，不必靠人记得。（同 V5.5 对触碰带上缘的处理。）

`StopRing` 的半径读取同步改为 `StopBandRadius()`——**光圈与判定共用同一个函数**，同源规矩不破（工具不许是第二套实现）。调试框与告警的读数也一并改为显示停止带而非保持距离。

### 4.5 取值依据是几何，不是手感

```
stopBandRadius ≥ 眼高 ÷ tan(垂直FOV / 2)      ← 平视时画面里最近的地面有多远
walkKeepDistance ≥ 眼高 ÷ tan(俯角上限)        ← 走到之后目标还留在画面内
```

眼高 1.7 m 时，第一式：FOV 60° → 2.94 m；51.28° → 3.54 m；45° → 4.10 m。达到此值，点画面下缘才真正进入纯停分支，此时**连点变成幂等操作**——慌乱胡点不再产生任何位移。这条性质比「停得快」更要紧：达不到时会出现一条传送带（想停 → 没停 → 以为没点中 → 再点 → 最近可点地面又在新位置前方 → 越点越停不下来）。

第二式：`1.7 ÷ tan(60°) ≈ 0.98`，故 `walkKeepDistance` **调至 1.0 正好落在下限上**。值得注意的是，1.0 本就是这个参数最早的取值——它原本是为「走过去」这个职能调出来的，后来被「停」征用才涨到 4.0。**本次修改等于把它调回原岗位。**

### 4.6 采用的参数组合

| 参数 | 在哪 | 值 |
|---|---|---|
| `Stop Band Radius` | V5 ·「停下来」 | 4.2 |
| `Walk Keep Distance` | V5 ·「我想看：停在多远」 | 1.0 |
| `Only Visible While Moving` | `StopRing` | 取消勾选 |

研究者实测：**「这回感觉控制起来更有把握了。」**

### 4.7 代价，及由它逼出的第二项改动

拆开之前，停止带边界与保持距离是同一个数，位移从边界处**连续地从零长起**（4.19 m → 走 0；4.21 m → 走 0.01 m）。

拆开之后：**4.19 m → 走 0；4.21 m → 走 3.2 m。边界上出现一个 3.2 米的跳变。**

这无法用调参消除——`walkKeepDistance` 越小跳变越大，两者是同一个量。它正是脚本注释警告过的那类东西（「几乎相同的两击走出明显不同的距离，被试会读成系统不稳定」）。

**之所以可接受，是因为这个跳变发生在一条画得出来的线上。**但由此发现一个配套缺陷——研究者指出：

> 「在停止状态下光圈是不显示的，这个时候被试当然不知道他点的地方是什么位置。」

被试恰好在最需要知道边界在哪儿的时刻（站定、正要判断这一下点在圈内还是圈外）看不见它。

**于是 `StopRing` 新增 `onlyVisibleWhileMoving`（默认 true = 旧行为）。取消勾选则光圈常驻。**改动只有 `Set()` 里一行；回放跳转入口同步尊重常驻，否则拖时间轴会闪。浓淡用既有的 `opacity` 压，不用可见性压——两者解决的不是同一个问题。

**由此修正一条早先的判断**：曾认为「停改成屏幕参照之后光圈可以删掉」。**拆分之后光圈成了承重件**，它标的是一个真实的行为断点。将来即便把停改成俯角判定，那条边界仍须以某种方式画出来，只是形状从地上的圈变成画面下缘的一条。

### 4.8 未采用但已论证的备选：停改为俯角判定

概念层给出过一个更彻底的方案：**停 = 点在画面下缘的俯角带内**，即 `turnDeadZoneAngle` 的垂直孪生。

优点：不受地形影响（俯角是相机自己的量，上下坡读法一样）；上限同样硬（垂直半张角 ≈ 25.6°）；不需要光圈。须处理的交叉是「近处植被也在画面下方」，优先级定为触碰优先、再判停。

**本轮未实施**，因为拆参数 + 光圈常驻已经解决了实测中的问题，而这一步会改变判定形状。**记录在此，留作后续若斜坡问题复发时的备选。**

## 五、旋转类问题二：聚焦目标 vs 环视浏览

### 5.1 问题性质

Psi 笔记：「【走过去】与【走过去】+【我想看】的动机区分——同一个点击，系统怎么知道该保持平视还是锁定目标。」研究者当时的判断是：**「这不是技术层面的，而是动机层面的。」**

具体症状：从远处看到一个感兴趣的对象，点它走过去，到站时它已经掉到画面下沿之外。而随便逛逛时，又不希望每点一下地面画面就要挪一下。**两件事需要的相机行为相反。**

**代码层的病根已查明**：`headPitch` 全脚本只由拖动与回正写入，**点击从不改变俯仰**，相机全程平视。视线没有被锁在目标上，所以走近的过程中目标自己往画面下方掉。

### 5.2 一个被实测推翻的方案：靠落点兜底

概念层曾提出：让落点保证「走到之后、平视状态下，命中点仍在画面里」，甚至进一步「让它落在画面下三分之一」。

**研究者用两张截图证伪了这个方案。**测试内容：取远处一个较低的植物为目标，走过去，到站后该目标已跑出画面之外。

证伪的机制是——**距离在两件事上方向相反**：

| | 退远的效果 |
|---|---|
| 俯角随接近而增大 | **缓解**（远处地面在画面里位置更高） |
| 近场遮挡（到站位置周围的蕨与高草） | **加剧**（目标更小，中间横着的植被更多） |

**结论：只要俯仰锁死在平视，「走过去看一个低处的东西」在任何距离上都做不成。**近了掉出画面，远了被挡住又太小。这不是参数没调好，是这条路上没有解。

由此产生的一条推论也被记下：**留住可见性和留住注意力不是一回事。**

### 5.3 一个被实测推翻的反驳（研究者自我修正）

更早的讨论中曾提出过按命中层区分聚焦/浏览，研究者当时反驳：**「如果被试对某一块贴图感兴趣，那么这个方案就不起效」**，且层判定无法分辨「贴图」与「实在对象」。

**本轮研究者基于实测撤回该反驳**：

> 「在我实际测试中，我发现几乎没有对贴图感兴趣的时候。真正感兴趣的，一定是那些有立体感、实在的对象。」

**这是本轮唯一一条由实测翻案的设计判断**，且翻案方向是从「不可行」到「可行」，值得记明。

### 5.4 修改思路：不读动机，只读命中层

与项目一贯做法同源——**把「猜意图」换成「查世界」**。

| 命中层 | 模式 | 视线 |
|---|---|---|
| Terrain | **浏览** | 不锁，保持平视 |
| Rock / DeadWood / Foliage 等其余 | **聚焦** | 锁在命中点上，走近时随之低头或抬头 |

**「聚焦 vs 浏览」这个区分因此不再需要被系统判断**——两种体验由被试点了什么自然分出，系统一次动机推断都不做。问题被取消，而非被回答。

Terrain 默认归浏览的理由：点地面通常是「我要去那儿」不是「我要看那儿」；若聚焦也管地面，走向一块远处空地会一路越走越低头——那既不是人走路的样子，也是**垂直光流最强的形态**（晕动风险）。

### 5.5 一次实现方向的错误，及其纠正

**首次实现把闸下在了偏航上**：浏览层不转身、聚焦层按死区转身。三处 `RequestTurnTowards` 调用点加了 `!browseThisTap` 守卫。

研究者当即指出该实现错了轴：

> 「我说的浏览层不转身，表达是错误的……我们这里要的是，摄像机是不是要低头或抬头？在浏览模式下，身体还是要转身，但是眼睛始终处于平视。」

**已全部回退，改为只管俯仰。**这一条写进了代码注释与 README：

> **聚焦与浏览的区别是「视线锁不锁」，不是「转不转身」。两种模式下身体转向完全一样，由 `turnDeadZoneAngle` 单独决定。**

错误的成因值得记：概念讨论阶段确实同时谈过偏航（内聚 / 锚融入）与俯仰（跟随 / 不跟），两条线并行且规则不同，实现时把两者的归属搞混了。**这从侧面说明「偏航与俯仰必须分开描述」这条结论本身是对的**——它们混在一起时连实现者都会弄错。

### 5.6 解决方案（V5.6）

**新增四个字段**（Inspector 新栏「聚焦 / 浏览」）：

| 字段 | 默认 | 作用 |
|---|---|---|
| `useFocusBrowseModes` | true | 总开关。关闭 = 完全退回 V5.5，可做 A/B |
| `browseLayers` | 留空自动填 Terrain | 勾选的层算浏览 |
| `focusPitchUpLimit` | 20° | 聚焦时视线向上能抬多少 |
| `focusPitchDownLimit` | 55° | 聚焦时视线向下能低多少 |

**新增视线锚状态**：`focusAnchorWorld`（世界坐标）+ `hasFocusAnchor`。锚钉在世界上不随人移动，所以走近时俯仰角自己就变了——「走过去时目标掉出画面」正是因为以前没有这个东西。

**新增 `UpdateFocusPitch()`**：每帧把 `headPitchTarget` 指向锚。

```
wanted = atan2(-(anchor.y - eye.y), 水平距离) × Rad2Deg
wanted = clamp(wanted, -focusPitchUpLimit, +focusPitchDownLimit)
wanted = clamp(wanted, -maxPitchAngle, +maxPitchAngle)   ← 与脖子极限取交集
```

**只写目标值（意图），不写实际值。**实际俯仰仍由既有的 `UpdateLookSmoothing` 缓入缓出地去追，于是**靠近限幅时自然减速，不会撞墙**——这正好兑现了研究者对情况 C（站着点树冠）提出的要求：「接近此阈值的时候旋转减速，超过此阈值的时候旋转不动。」减速是免费的，不需要额外机制。

### 5.7 四条设计决定

**一、`browseLayers` 只给一个遮罩，不给两个。**聚焦与浏览是二分且穷尽的：任何一次命中不是这个就是那个。给两个遮罩会产生「两边都勾」与「两边都不勾」这两种没有定义的配置，而且它们不报错，只表现为某些层行为莫名其妙。

**二、俯仰按世界坐标算，不按身体朝向算。**（研究者在「情况 D」讨论中明确选定「相对世界算」方案。）若按身体算，身体慢慢转正的过程中目标会在画面里斜着划过去；按世界算则稳稳待着，身体转正只是让它移向画面中心。

**三、上下限不对称是有意的。**向上幅度小，两个独立理由：行为上，人走路时视线偏向前方与稍下，向下取样是短促的，而持续大幅仰头走路不是人的样子；生理上，向上的俯仰叠加前向平移产生强垂直光流，而**垂直光流对晕动的贡献大于水平**。向下 55° 是需求逼出来的——眼高 1.7 m、停在 1.0 m 处时需约 60° 才能盯住脚边的东西，55° 略留余量。

`focusPitchDownLimit` 与 `maxPitchAngle`（拖动极限 60°）是两个数，这一点须记明：**那个约束的是被试自己想看多低，这个约束的是系统替他低多少头。系统的自作主张应当比被试的主动动作更保守。**

**四、锚按事件改变，不按时间衰减。**锚一经设定就保持住，直到下一次点击替换它、或被试拖动屏幕。**拖动会立刻清掉锚**——研究者已定的规矩：「点击引起的旋转是系统的解释，可以被限制、被减速、被拒绝；拖动引起的旋转是被试的直接控制，一比一，不打折。」系统的解释不该在那一刻跟他抢方向。

**没有按时间自动松开的机制。**理由见第六节。

### 5.8 两处接缝的处理

**一、锚与回正抢同一个量。**`returnHeadOnMove` 会把 `headPitchTarget` 拉向 0，聚焦要拉向锚。`UpdateFocusPitch()` 写在回正之后——**谁后写谁说了算，而聚焦是被试刚刚用一次点击明确表达的意图，回正只是一个默认倾向。**

**二、调试框必须显示模式。**新增一行：

```
模式：聚焦（锁在锚上，俯仰目标 12.4°　上限 -20°/+55°）
模式：浏览（视线平视，不锁）
模式：聚焦（锚已被拖动清掉）
```

**这一行是必须的**：两种模式在静止画面上看不出区别，差别只在走过去时视线跟不跟。不显示出来，一次正常的「没跟」会被当成故障去查——**本项目这类误诊已经发生过多次**（方案F 第二节记录的六次静默失效同源）。

### 5.9 一个已知的参数串岗（未修，已记录）

聚焦时视线转向锚的**快慢**，目前由「环顾（拖动）」栏的 `lookSmoothTime`（0.12）与 `lookMaxAngularSpeed` 控制——**与拖动共用同一条惯性曲线**。而两者要的快慢正好相反：拖动要跟手所以快，系统自己发起的转动要稳所以慢。

研究者实测反馈：「现在转的好快，但是控制不了好像。」诊断确认后，研究者决定**暂不拆分**：

> 「这个 `Look Smooth Time` 是可以控制的，只不过这些参数同时控制两组动作，在 UI 面板上很难分类，在使用的时候会忘记怎么调。先这样吧，凑合用。」

**记录在此的理由**：这是那种半年后会让人困惑的东西——调拖动手感时莫名其妙改变了抬头速度，而面板上看不出任何关联。若将来需要分开，加一个独立时间常数即可，改动很小。

顺带记明：**这已是本项目第四次遇到「曲线不对，不是速度不对」**（V1 身体转向匀速→缓入缓出、V3 头部转动刚性→惯性、V3 回正漂移、本轮聚焦俯仰）。前三次已升为通则；本次的形态略有不同——**不是曲线错了，是两件性质相反的事共用了同一条曲线。**可视为该通则的推论：**系统发起的转动与被试直接控制的转动，不应共用同一条曲线。**

### 5.10 代价

**一、新增了垂直方向的纯旋转来源。**站着不动点树冠 → 身体不动、镜头抬起，这是一次**没有任何平移伴随的垂直纯旋转**，原系统里不存在这一格。垂直纯旋转对晕动的贡献比水平大。频率取决于被试多常点高处，**须在 iPad 上实测，桌面大屏的读数不作数。**

**二、矮处对象的聚焦只做到「看得见」，未做到「看着它」。**`focusPitchDownLimit` 55° 加上 `walkKeepDistance` 1.0 能保证目标留在画面内，但它会在画面下缘而非中心。**这笔账挂着，等真被试来还**：若有人报告「我想看那丛草但它老在画面底下」，那时再动。

## 六、被推翻或修订的旧结论

| 结论 | 处置 |
|---|---|
| 「多点几下 = 聚焦」（本轮讨论中提出） | **删除**。它是方案B 第七节已作废条目（反复点击是空转）的复活 |
| 「锚衰减」：系统静默把视线锚移回视野中心 | **删除**。研究者判定为冗余概念——它不改变任何画面，唯一后果是改变下一次点击的偏角基准，构成**不可见的系统状态**（方案D 2.5.5 判为坏的那一类） |
| 「锚脱落」：锚超出余光则丢弃、视线回到前方 | **删除**。推敲后发现该情形在纯点击操作下几乎不可能发生；且「回到前方」预设了一个独立存在的默认朝向，而摄像机朝向没有第二个来源 |
| 「按命中的是地面还是对象来决定有没有看目标」（修正三） | **删除**。研究者指出所谓对象可能只是一块贴图，该分类不可靠；把设计判据架在已知不可靠的 C 类事实上，等于制造一批静默失败 |
| 「靠落点兜底解决矮处对象」 | **删除**，被实测证伪（见 5.2） |
| 「停止带对所有层统一」 | **删除**，实现前推翻（见 4.3） |
| 「停改成屏幕参照之后光圈可以删掉」 | **修订**。拆分之后光圈成了承重件，标的是一个真实的行为断点 |
| 「聚焦/浏览管的是转不转身」 | **修订**。管的是视线锁不锁，只涉俯仰（见 5.5） |
| 「贴图会让层判定失效，故层判定方案不可行」（研究者旧判断） | **研究者本轮自行撤回**，依据是实测观察（见 5.3） |

## 附：本轮确立或复用的判据

1. **概念推导到「规则该长什么样」即止，下一步是去代码里找它，不是去设计它。**（本轮最大教训，见第二节）

2. **屏幕参照优于世界参照。**任何用世界距离定义、而被试用屏幕操作的量，都会随地形变形而不可预期。`turnDeadZoneAngle` 成立、停下光圈失效，同一条道理的两面。

3. **系统发起的转动与被试直接控制的转动，不应共用同一条曲线。**（第四次「曲线」问题的推论，见 5.9）

4. **不可见的系统状态是坏的。**锚衰减因此被删——它不改变画面，却改变下一次点击的结果。

5. **取消问题优于解决问题。**本轮五个问题里两个被取消。取消掉的问题不会在下一轮以别的形状回来。

6. **一个数不许管两件方向相反的事。**`walkKeepDistance` 的拆分即此。这类耦合在面板上不可见，只能靠推演发现。

7. **系统的自作主张应当比被试的主动动作更保守。**`focusPitchDownLimit` 55° < `maxPitchAngle` 60° 即此。

8. **凡是「同样的画面、不同的结果」，且原因不可见，就是设计缺陷。**（沿用方案D 2.5.5）
